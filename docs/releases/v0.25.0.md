# v0.25.0 — Independent Core, Connector and Agent Bridge lifecycles

This note describes the integrated v0.25.0 source and the scope of recorded acceptance. The previous stable baseline was v0.24.2. The [release checklist](../v0.25.0-release-checklist-2026-11-21.md) records candidate readiness and authorization; the immutable GitHub tag, Release assets and publication verification establish distribution status. The existence of this note is not evidence of publication or a production upgrade.

## Changes

- Independent named Core, Connector and Agent Bridge identities and lifecycles. A host can deploy file-only Cores, independent owned Core/Bridge pairs, or multiple Cores sharing an owner-controlled Bridge. The Bridge modes are `disabled`, `owned` and `shared`.
- Signed v2 Core grants authenticate Core identity, limit aliases/methods and isolate task ownership. The grant path rejects submission continuation and idempotency keys. Native macOS owned mode instead uses private manifest/policy/IPC checks. Shared-Bridge authorization is not implied by a common host user. Each platform retains its native mechanism; no central instance manager or cross-OS private-wire compatibility is required.
- Linux: Compose-based Core and optional Connector services, direct HTTP (with an external reverse proxy if needed), Cloudflare and OpenAI Tunnel selection, and an optional host-side systemd Agent Bridge. This keeps existing host Agent runtimes accessible. Named Linux uses distinct Core/Bridge IDs, one service per Connector provider per project, one Agent/Repo Ops-enabled alias (slot 01) and up to 32 initial Core grants.
- macOS: native arm64 Apple Silicon/macOS 27/APFS, signed SMAppService lifecycle; named file-only/owned Core and independently managed Connectors. Shared Core requires an existing separately configured owner, one Agent-enabled workdir, no Repo Ops or named Connector staging.
- Windows: native current-user Task Scheduler and Job Object lifecycle, named components, signed named-pipe grants and private Windows ACLs. No WSL or VM is required. Owned native pair shares its instance ID; shared owner uses distinct grants (up to 16 initial Cores). Native initial provisioning is create-only on macOS/Windows; no general in-place upgrade or online rotation.

- Named OpenAI HTTP Connector requires static Core bearer; OAuth uses a separate authorization service and does not share Connector credentials. Direct HTTP needs no Tunnel. File-only needs no Bridge; Repo Ops remains independent of Agent delegation. Optional tool availability depends on deployment and policy.
- Seven operational Skills and their references use a skills-only portable Plugin. The Registry OCI package remains a separate local read-only Docker entry, not full deployment.

See the [accepted native-first ADR](../architecture/v0.25.0-native-platform-boundaries.md) and the [Linux](../../deployment/linux/README.md), [macOS](../../deployment/macos/README.md) and [Windows](../../deployment/windows/v0250-native-operations.md) deployment guides.

## Acceptance evidence

All four ordinary GitHub CI workflows passed on integration head `e562f21f86bd444da7507a05fc96778981883a1a`: [Container](https://github.com/NTLx/ServerFS_MCP/actions/runs/44874390138), [macOS Native](https://github.com/NTLx/ServerFS_MCP/actions/runs/44874390109), [Windows Native](https://github.com/NTLx/ServerFS_MCP/actions/runs/44874390141) and [Windows Agent](https://github.com/NTLx/ServerFS_MCP/actions/runs/44874390112). PR #43 merged into main at `fffc0adb8341edb30ac7b03e72a017ca95b8c83d`. Those runs are integration evidence, not the version-bumped release SHA's acceptance.

- Linux: recorded dedicated Cloudflare public authentication, MCP file access, isolated Connector lifecycle and cleanup; offline OpenAI client readiness is not real public registration/discovery.
- macOS: recorded native shared-Core registration, Bridge restart/revocation and reauthorization, controlled Connector-only restart, public MCP and SSE, and isolated file-only Core/synthetic Connector recovery. Production Connector abrupt-exit recovery, nested delegated MCP authorization and cross-region/multi-client behavior remain unverified.
- Windows: prior frozen candidate artifacts passed owned/shared lifecycle, signed IPC, public dual Cloudflare and no-model native isolation as documented in the [integration handoff](../diagnostics/v0250-windows-integration-handoff-2026-11-21.md). Strict real-provider I11-B acceptance and isolated real OpenAI public ingress remain open.

These earlier platform-specific measurements do not establish equivalent live acceptance for the final release artifact. No same-session SSE replay or production rollout is claimed. Exact-release-SHA builds, packaging, required native/public acceptance and explicit authorization remain separate gates. See the [release checklist](../v0.25.0-release-checklist-2026-11-21.md) for outstanding gates.
