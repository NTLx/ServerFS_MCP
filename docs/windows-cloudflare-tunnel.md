# Windows native Cloudflare Connector

Use this procedure on Windows 11 x64 with local NTFS and an already prepared named HTTP Core. The Cloudflare Connector is a current-user task with its own Connector ID, pinned executable, private token and state. It does not own Core or Bridge.

1. Prepare a matching installed controller and offline Connector runtime as described in [Windows native component operations](deployment/windows/v0250-native-operations.md#5-optional-add-independent-connectors).
2. Identify the exact target Core ID, loopback port and configured hostname. Confirm authenticated local MCP readiness and select a distinct external remotely managed Tunnel and hostname. See [Cloudflare Connector](cloudflare-tunnel.md) for public route and admission.
3. Supply trusted SHA-256 pin and absolute protected paths to `cloudflared.exe` and the token file. Use the initial `configure-v25-connector.py` helper with the exact `--instance`, `--connector-id`, and `--component cloudflare`. It copies inputs and publishes a fresh manifest, not a running task. The helper rejects known duplicate Tunnel identities but cannot check all older/manual peers: if `manual_cloudflare_peers_unchecked` is nonzero, resolve those identities before activation.
4. Using the trusted installed controller interpreter, run `-I -B -m serverfs_mcp.windows_v25.cli cloudflare --instance <core-id> --connector-id <connector-id> install`, then the same command with `start` instead of `install`. Check status; verify provider registration, public HTTPS, authenticated MCP and denied admission using the intended remote client.
5. For restart use the scoped component action; verify unrelated process/task identities and establish a fresh session. For retirement, stop then uninstall the exact task; private inputs remain. The helper is create-only, not token rotation. Preserve failure evidence and follow an explicit migration/retirement plan.

Do not bypass DACL/reparse-point checks, use legacy group lifecycle commands, or delete/reassign remote Tunnel resources without separate authorization. Local token validation does not establish route ownership or public acceptance. See the [release checklist](v0.25.0-release-checklist-2026-11-21.md).
