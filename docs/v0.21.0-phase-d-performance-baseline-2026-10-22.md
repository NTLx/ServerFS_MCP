# ServerFS v0.21.0 Phase D — Pre-instrumentation Performance Baseline

Status: **Baseline established on the Linux/VPS reference environment. Agent hot-path instrumentation has not started yet.**

Product baseline: `b75d7e43a9331470bc8525a236319728dc5b72dc` (`feat: add v0.21 common service status`). The benchmark harness is a maintainer-only file outside package wheel paths and does not change runtime behavior.

Date: 2026-10-22.

## 1. Purpose

Phase D will add bounded Agent task/queue/lease/recovery observations. Before changing those hot paths, this record freezes a reproducible baseline so later measurements compare the same deterministic workload before and after instrumentation.

The baseline deliberately uses the existing `fake` Agent runtime, temporary private state, one writable workdir, and no Jev/provider/Tunnel/network activity. This isolates ServerFS/Bridge scheduling, SQLite task persistence, writer leases and local event-loop behavior from external-provider latency.

## 2. Benchmark harness

Maintainer tool:

`agent_bridge/benchmarks/v021_phase_d_baseline.py`

The script uses only the Python standard library plus the existing `serverfs_agent_bridge` package. It outputs one JSON document and measures:

- Bridge service construction and `start()` latency;
- idle process CPU and Linux current RSS (`/proc/self/status` `VmRSS`);
- `submit_task()` call latency;
- external submit-to-terminal latency;
- durable `created_at -> started_at` queue wait;
- durable `started_at -> completed_at` execution duration;
- uncontended writer-lease acquire + release latency;
- contended writer-lease acquisition that must fail with `WORKDIR_BUSY`.

The benchmark uses fresh temporary directories and no persistent user service state. It never starts a real provider or performs network egress.

Smoke validation passed with reduced counts, and Bridge-project Ruff lint/format checks passed.

## 3. Reference environment

Three independent Python processes were measured on the VPS:

- OS: Linux x86_64;
- kernel: `6.8.0-136-generic`;
- glibc: 2.39;
- Python: 3.12.13.

Per-run parameters:

- startup iterations: 20;
- task iterations: 100;
- lease iterations: 1000;
- contention iterations: 100;
- idle interval: 0.5 s;
- task timeout: 30 s.

All three runs completed successfully. Process wall times were approximately 11.8 s, 7.7 s and 7.8 s. The slower first run is retained rather than discarded because it is useful evidence of host/cache noise.

## 5. Evidence-based budget refinement before instrumentation

The plan's provisional percentage budget is below measurement resolution for this workload:

- median idle CPU is only 0.0643%; a 5% relative increase is ~0.003 percentage points;
- startup RSS delta is 8 KiB; a 5% relative increase is below normal page/accounting granularity.

Using those relative percentages would create false precision. Before changing the hot path, Phase D therefore freezes the following measurable release criteria for Agent observation instrumentation:

1. **No background observer loop/thread/timer.** Metrics update only at existing task/lease/recovery transitions. When the Bridge is idle, observation performs no periodic work.
2. **Idle memory:** post-start observation state may add at most **256 KiB** RSS on the Linux reference benchmark, and RSS must show **no continuing increase during the idle interval** attributable to observation.
3. **Submission overhead:** cross-run median of `submit_task` p95 may increase by at most **5.0 ms** versus the 17.424 ms baseline, using the same three-run benchmark shape.
4. **Lease manager primitive:** the instrumentation design should not modify `LeaseManager.acquire_exclusive()` itself unless required. If it does, cross-run median lease acquire+release p95 must not increase by more than **0.10 ms**. Prefer timing around the existing call in `BridgeService` so the locking primitive remains unchanged.
5. **MCP request path:** Phase D Agent observation code must not be added to ordinary filesystem MCP request handling; therefore the expected added latency to non-Agent MCP requests is structurally zero. Existing root regression tests remain the compatibility gate rather than a noisy microbenchmark for an untouched path.
6. **Task end-to-end timings:** submit-to-terminal and durable queue/execution figures are retained as diagnostic evidence. Because the three baseline runs vary substantially, they are reviewed for gross regressions but are not used as a single-digit hard threshold.

These refinements preserve the original intent—bounded overhead—while making the release gate observable on the available reference host instead of pretending sub-page/sub-scheduler precision.

## 6. Platform scope

This is the pre-instrumentation baseline for the **available Linux/VPS reference environment**. It is not a macOS/Windows performance claim.

Phase F native acceptance should rerun the same maintainer benchmark shape where the platform Bridge environment is available. Unsupported/unmeasured platform performance remains `Not verified`; Linux measurements are not silently inherited by another platform.

## 7. Next implementation constraint

Phase D may now instrument Agent task outcome, queue wait/depth, execution duration, writer-lease acquisition/contention and recovery/reconciliation, subject to these constraints:

- preserve provider/package isolation;
- no exporter/network/listener;
- no new durable high-volume event table;
- no task/workdir/session/provider identity in metric labels;
- no free-form exception/error text in bounded observations;
- no change to writer-lease/recovery-guard semantics;
- after implementation, rerun the exact benchmark shape above three times and compare before/after evidence.
