# ServerFS v0.21.0 Phase E — Exporter Decision

Status: **COMPLETE — no Prometheus/OpenTelemetry exporter will be added in v0.21.0.**

Date: 2026-10-22.

## 1. Decision

ServerFS v0.21.0 will ship the internal observation contract, bounded metric catalog, common native service-status projection, Agent Bridge process-local observations, and existing operator diagnostic/publication surfaces **without adding a metrics exporter**.

This is an explicit product/architecture decision, not unfinished work. Phase B–D established a transport-neutral semantic model first; Phase E evaluated whether exposing that model through Prometheus or OpenTelemetry adds enough operator value to justify a new deployment/security/support surface. Current evidence does not justify that expansion.

No exporter package, listener, RPC method, port, scrape endpoint, telemetry egress path, collector process, persistent telemetry store, configuration key, optional dependency group, or public metrics contract is added in v0.21.0.

## 2. Evidence reviewed

The decision uses the completed v0.21 evidence:

- Phase A inventory: existing `doctor`, native service status, Tunnel diagnostics, Agent state, structured logs, and the external least-privilege host-observability recipe already provide distinct operator surfaces without requiring a generic metrics server.
- Phase B: a closed transport-neutral catalog and redaction/cardinality policy exists independently of any exporter.
- Phase C: supported native service status can explicitly project the common contract while preserving default platform-native JSON and deeper diagnostics.
- Phase D: Agent task/queue/lease/recovery metrics are bounded and process-local; the Bridge-local catalog has a 416-series theoretical ceiling, contains no identity/free-form labels, and meets the frozen Linux/VPS performance budgets.

The exporter decision therefore does not need to compensate for a missing semantic model. The semantic foundation already exists and remains reusable if a later operator requirement justifies an exporter.

## 3. Operator-demand assessment

No concrete v0.21 operator requirement identifies a monitoring system that must scrape or receive ServerFS-native metrics. The required operational questions in `dev_plan_v0.21.md` are answerable through the converged status/diagnostic contract and existing read-only publication guidance.

Adding an exporter without a named consumer would create an interface first and discover the operational requirement later. That contradicts the v0.21 design rule: **internal observation contract first; exporter only when evidence justifies it.**

The existing host-observability recipe intentionally keeps host collection outside ServerFS core and publishes allowlisted generated facts through a read-only workdir. Phase A explicitly preserved that low-authority boundary rather than granting ServerFS shell, Docker socket, broad log, or monitoring-daemon authority.

## 4. Prometheus-compatible pull assessment

A Prometheus-compatible exporter would require a scrape surface. Even if bound to loopback/private addresses and disabled by default, it would introduce additional design obligations that v0.21 does not otherwise need:

- listener lifecycle and port ownership;
- bind/default exposure rules on Linux, macOS, and Windows;
- Host/Origin/authentication expectations where non-loopback use is requested;
- container port/publication guidance on Linux;
- per-user native service lifecycle integration on macOS/Windows;
- scrape freshness/reset semantics and operator expectations around process-local counters;
- packaging and support of a new externally consumed wire contract.

The internal metric catalog is safe enough to project, but cardinality safety alone is not sufficient justification for a listener. v0.21 explicitly has a non-goal of adding network exposure merely to make probes easier.

**Prometheus decision for v0.21: not approved.**

## 5. OpenTelemetry assessment

An OpenTelemetry integration would avoid requiring a Prometheus scrape endpoint in some topologies, but introduces a different set of obligations:

- collector/endpoint configuration;
- optional outbound network behavior and explicit egress consent;
- authentication/TLS/environment configuration questions;
- SDK/exporter dependency footprint and packaging isolation;
- retry/buffering/failure behavior and shutdown semantics;
- resource identity policy, which risks reintroducing hostname/user/process identity fields intentionally excluded from the v0.21 common contract;
- cross-platform validation against multiple collector/deployment topologies.

A disabled-by-default implementation could make steady-state overhead near zero, but the support/security surface would still exist and no concrete collector requirement currently demands it.

**OpenTelemetry decision for v0.21: not approved.**

## 6. Security and authority review

The no-exporter decision preserves the current boundaries:

- no new network listener or published port;
- no new outbound telemetry connection;
- no new authentication or authorization surface;
- no server/collector credential storage;
- no expansion of ServerFS host privileges;
- no change to workdir authorization, writer leases, recovery guards, provider sandbox/approval, Tunnel ownership, or native service lifecycle;
- no new path by which task IDs, workdir identity, provider/session identity, model IDs, prompts, errors, URLs, hostnames, principals, or private paths could leave the process.

The internal observation model remains operational evidence only. It is not an audit log and does not prove provider stop, authorization, filesystem safety, or durable history.

## 7. Dependency and availability review

Core/root and Agent Bridge dependency sets remain unchanged. There is no optional exporter package to fail import, bind, connect, flush, retry, or shut down.

Therefore exporter-disabled overhead is exactly zero because no exporter implementation exists, and exporter failure cannot affect MCP or Bridge service availability.

This also preserves the Agent Bridge package-independence boundary: the Bridge does not need to import `serverfs_mcp`, and the root package does not need provider/Bridge dependencies merely to expose telemetry.

## 8. Platform parity review

Phase F still needs real native acceptance on Linux, macOS, and Windows. Introducing an exporter before that acceptance would multiply the platform matrix by adding listener/collector/service-lifecycle behavior to each environment.

The no-exporter decision allows Phase F to validate the actual v0.21 product claims first:

- Linux container/deployment diagnostics;
- supported macOS native arm64 service status/lifecycle boundary;
- native Windows current-user lifecycle/status boundary;
- shared contract/redaction behavior.

No platform is required to host or connect to a monitoring backend for v0.21 acceptance.

## 9. Revisit triggers

A later version may reopen the exporter decision when at least one concrete operator requirement exists. The design review should identify, before implementation:

1. the actual consumer (for example a Prometheus-compatible scraper or an OpenTelemetry Collector);
2. pull vs push topology and expected network boundary;
3. bind/egress/authentication/TLS policy;
4. supported Linux/macOS/Windows deployment matrix;
5. whether process-local reset semantics satisfy the consumer;
6. exact optional dependency and packaging isolation strategy;
7. disabled-path zero-overhead evidence;
8. failure isolation, cardinality, redaction, and performance tests.

The existing Phase B catalog and Phase D Bridge observations should be projected directly. A future exporter must not create a second semantic model or add arbitrary identity dimensions.

## 10. Gate verdict

**PASS.** Phase E records an explicit **no-exporter-for-v0.21** decision after reviewing operator demand, sensitivity/cardinality, topology, dependency footprint, offline behavior, packaging, platform parity, failure isolation, and measured runtime cost.

The core product requires no exporter dependency or configuration; no exporter failure can affect service availability; no new listener or telemetry egress exists. Phase F may proceed with native platform acceptance and release-facing documentation.
