# v0.20 Phase D — MCP Registry OCI Probe

Date: 2026-10-22
Baseline: `main` at `840aae50a459565dbe3f8c9658ec423f070998ec`
Scope: read-only design probe plus this decision record. No Registry publish or authenticated API call was made.

## Decision and implementation status

**Status: Phase D local acceptance complete.** The frozen Phase D decision is implemented in `server.json`, the Dockerfile, vendored schema, offline validator/tests, version sources and root/container CI. The configured workspace is mounted read-only at `/workdirs/01` and assigned to the fixed `workspace` alias. The initial direct container smoke failure is diagnosed: the image had no `/workdirs/02..16`, and the fixed 16-slot registry scan raised `WorkdirError` on missing slot 02. A temporary-filesystem reproduction confirmed that exact failure and succeeded after adding sentinel-only directories. The Dockerfile creates all 16 image defaults as UID/GID 10001-owned, mode 0555 directories containing only a mode 0444 `.serverfs-disabled`; a real bind mount covers its slot. A scratch image built successfully; a named container remained running, and one targeted root MCP client loopback call returned alias `workspace` with `access=read-only`; the container was stopped and removed. Focused tests passed (92); root Ruff check/format passed; full root pytest passed (1691 passed, 317 skipped); version-lock checks and `git diff --check` passed. **Not verified:** Registry client OCI + Streamable HTTP installation/interoperability. `/v0.1/validate` was not exercised.

Describe the existing OCI image as its actual local **Streamable HTTP** service. The 2025-12-11 schema permits `streamable-http` on a package (local) transport and requires a URL. The existing image starts the HTTP server, and HTTP is the supported Linux/container ingress. Use the fixed loopback endpoint `http://127.0.0.1:8000/mcp`, with Docker runtime arguments that publish only `127.0.0.1:8000:8000`. This is an accurate manifest description only if the Registry consumer honors those arguments and the local package URL as expected; that OCI + Streamable HTTP installer behavior is **Not verified**.

Do not label the current image `stdio`: its default command is HTTP. Do not point a package at an operator's remote Compose service: that is not a local package endpoint and would falsely describe an installation artifact. Do not add a new stdio entrypoint in Phase D merely to fit the official OCI example. Reconsider a Linux/container-only stdio entrypoint only if a concrete Registry client proves OCI packages must use stdio and the implementation can provide a supported, safe configuration/mount contract. It would be a new runtime surface, not a metadata-only fix.

If preview validation or a real target client rejects OCI + local Streamable HTTP, the minimal honest fallback is to defer the OCI package entry until the question is resolved; a separate `remotes` declaration is appropriate only for a real stable public HTTPS endpoint operated by ServerFS. Do not silently relabel HTTP as stdio.

## Findings

Evidence labels: **Verified** means directly established by the pinned local baseline or official source; **Inference** is a design conclusion from that evidence; **Not verified** means no direct evidence was obtained.

### 1. Schema constraints (2025-12-11)

- **Verified:** The dated schema is Draft 7. `Package.registryType` is a string whose examples include `oci`; `identifier`, `registryType`, and `transport` are required. `runtimeHint`, `runtimeArguments`, `environmentVariables`, `packageArguments`, and package `version` are optional in the schema. `runtimeArguments` are described as arguments to the package runtime (for example Docker), and the schema says `runtimeHint` should be supplied when runtime arguments are present. `environmentVariables` is an array of named input values.
- **Verified:** `Package.transport` is a `LocalTransport` union accepting `stdio`, `streamable-http`, or `sse`. The Streamable HTTP branch requires both `type: "streamable-http"` and `url`; the schema URL pattern accepts `http://`, `https://`, or a template beginning with a variable. Package transport URL variables can resolve from argument `valueHint`s, argument names, or package environment variable names. It does not define a special OCI-only transport rule.
- **Verified:** The schema does not make `runtimeHint` or runtime args mandatory for OCI and does not itself require environment variables. The descriptions' “should” language for runtime hint is advisory schema text, not a `required` constraint. The schema does not prove a particular client's OCI launch semantics. `NamedArgument` is an input value with a flag name and is documented as `--flag={value}`; the manifest therefore encodes the Docker boolean as `--rm=true`, rather than using a valueless named argument.
- **Verified:** An OCI image identifier is documented as `registry/namespace/repository:tag`; a digest may be used in place of a tag. OCI ownership requires the image annotation `io.modelcontextprotocol.server.name` to equal the manifest server name.
- **Sources:** [dated server schema](https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json), [Registry generic server.json reference](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/generic-server-json.md), [OCI package type documentation](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/package-types.mdx).

### 2. OCI + Streamable HTTP examples and URL semantics

- **Verified:** The official OCI package documentation's example uses `registryType: "oci"` with `transport.type: "stdio"`. The reviewed official OCI example does not demonstrate `streamable-http`.
- **Verified:** The schema permits Streamable HTTP in `Package.transport`, which is explicitly local/package context, and requires a URL. Its documented package URL template can interpolate defined package inputs, but there is no special “container localhost” rule in the schema.
- **Not verified:** No direct official example or implementation evidence was found that an official Registry installer launches an OCI package with Streamable HTTP, maps its port, waits for readiness, or resolves a local URL against a dynamically assigned host port. This probe did not establish that such an OCI package is already registered in production.
- **Inference:** If a target installer runs `docker run` and passes a fixed host port mapping, `http://localhost:8000/mcp` is coherent with `-p 8000:8000`. A random host port is not representable as a fixed URL unless the client has a documented substitution/port-discovery contract. A URL such as `http://serverfs-mcp:8000/mcp` would refer to a Compose/Docker network name, not reliably to the local user's host.
- **Source:** [OCI package type documentation](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/package-types.mdx) and [dated server schema](https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json).

### 3. Actual Linux/container entrypoints and transport

- **Verified:** At this baseline, `Dockerfile` uses `CMD ["python", "-m", "serverfs_mcp"]`; `src/serverfs_mcp/main.py` builds settings from environment and serves the Streamable HTTP app. The image exposes 8000; the HTTP endpoint defaults to `/mcp`. The base Compose service runs this image command, while `compose.http.yml` publishes host port 8000 to the container port. Thus the image default is HTTP.
- **Verified:** The `serverfs` CLI script exists in the built Python environment, but `src/serverfs_mcp/cli.py::cmd_serve` rejects Linux (`native serve is supported only on Windows and macOS 27 (Apple Silicon)`) before starting stdio. Therefore there is no Linux-usable `serverfs serve` entrypoint in this baseline. Windows/macOS `serverfs serve` documentation is not evidence of a Linux runtime.
- **Verified:** Linux stdio is not an advertised direct container ingress in the maintainer invariants. Current Linux deployment shapes are the outbound OpenAI Secure MCP Tunnel and opt-in generic Streamable HTTP.
- **Source:** [Dockerfile](../Dockerfile), [Compose base](../compose.yml), [HTTP Compose overlay](../compose.http.yml), [CLI implementation](../src/serverfs_mcp/cli.py), [main entrypoint](../src/serverfs_mcp/main.py), [maintainer invariants](maintainers/invariants.md).

### 4. Whether to add a narrow stdio entrypoint

- **Inference / recommendation:** Not for the minimum Phase D change. It would require a Linux/container-only launch path wired to the existing environment configuration and MCP server construction, plus subprocess/wire tests and a documented container input/mount contract. The Registry's stdio OCI example is evidence that stdio is a supported pattern, not evidence that ServerFS's HTTP image should be relabeled or that the Registry requires stdio.
- **Inference:** Keep the default image and manifest aligned on HTTP. Declare `runtimeHint: "docker"` and fixed runtime arguments only when verified against the intended client (for example `run`, interactive stdio if required by that client, and `-p 8000:8000`); preserve the image's actual command rather than override it. Pair the package transport with the corresponding fixed local URL. Since client handling is **Not verified**, do not claim this completes interoperable Registry installation until a consumer probe passes.
- **Risk boundary:** A future stdio adapter must not weaken current confinement, configured workdir policy, non-root execution, read-only filesystem, or other container hardening. Its presence must not be inferred from the cross-platform `serverfs serve` CLI name.

### 5. GitHub personal namespace spelling

- **Verified:** The local repository's remote owner is recorded as `NTLx`, and the user identifies the GitHub login/repo owner as `NTLx`. Official docs describe GitHub namespaces as `io.github.{username}`; the schema's name pattern allows upper- and lowercase characters.
- **Recommendation:** Preserve the supplied spelling as `io.github.NTLx/serverfs-mcp`; do not lowercase or otherwise normalize it based on assumption. Confirm namespace acceptance through the official publisher's GitHub login/validation flow before publication.
- **Not verified:** The publisher-auth implementation's case normalization/matching behavior was not independently inspected or exercised. The GitHub API probe did not return evidence in this run, so the canonical account login casing beyond the provided repository owner was not independently checked.
- **Sources:** [publisher CLI namespace/auth docs](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/cli/commands.md), [schema name pattern](https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json).

### 6. Repository ID and version alignment

- **Verified:** The schema's optional `repository.id` is a string and specifically says GitHub publishers should obtain it from `gh api repos/<owner>/<repo> --jq '.id'`; it is intended to remain stable across renames and change if a repository is deleted/recreated.
- **Recommendation:** If `1375202485` is confirmed as the current GitHub API ID for this repository, record it as the string `"1375202485"`. Using the stable forge ID is appropriate and recommended for repository identity. This probe did not independently confirm the number against GitHub, so that value is **Not verified here**.
- **Verified:** Top-level `version` is required. Package `version` is optional; if present it must be a specific version, and `latest`/ranges are disallowed. The schema does not itself require the top-level version and OCI tag/package version to be identical.
- **Project decision:** The v0.20 plan requires the manifest, package tag/version, project version, release tag and image metadata to agree. Follow that stronger project invariant: for the v0.20 release entry use top-level `version: "0.20.0"`, a stable OCI tag `0.20.0`, and package `version: "0.20.0"` if supplied. Do not put 0.20.0 metadata into the current 0.19.0 baseline artifact.
- **Sources:** [dated server schema](https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json), [v0.20 plan §6](../dev_plan_v0.20.md).

### 7. Deterministic validation and preview endpoint

- **Recommendation (offline):** Vendor the exact official 2025-12-11 schema in a clearly versioned repository path, record its source URL and SHA-256, and validate with Python `jsonschema` as a dev/CI-only dependency (never a runtime image dependency). Add a small validator that also checks project/manifest/package versions, server name versus Docker label, immutable OCI reference, and allowed transport assumptions. This is simpler and more deterministic than downloading mutable `main` schema or contacting Registry from ordinary CI. Pin dependency through the existing lockfile. The source schema is Draft 7; use a validator that checks the schema and `format` handling deliberately rather than assuming formats are enforced automatically.
- **Verified:** Official API documentation describes `POST /v0.1/validate` as validating `server.json` without publishing and identifies it as the operation used by `mcp-publisher validate`.
- **Not verified:** The reviewed official API docs do not state clearly whether anonymous callers may invoke `/v0.1/validate`; they document namespace authentication for publishing, but that alone does not prove the validate endpoint is unauthenticated. No request was made. Treat it as a manual, non-blocking supplemental probe until its auth behavior is checked. It must not replace offline validation or block PRs on service availability.
- **Sources:** [official Registry API docs](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/official-registry-api.md), [generic Registry API docs](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/generic-registry-api.md).

## Phase D implementation

Final audit: the structured runtime argument, workspace input, and environment guards passed the focused negative and positive manifest tests, Ruff checks, and offline validator.

Implemented:

1. Added root `server.json` with the maintainer-confirmed GitHub namespace spelling and repository ID `1375202485`, actual HTTP package transport, explicit Docker runtime declaration, fixed loopback URL/port mapping, one read-only workspace mount, and exact `0.20.0` package/image versions.
2. Add the OCI name label to `Dockerfile` and set its value exactly equal to `server.json` `name`.
3. Vendor the dated schema and add one offline validator plus focused tests for schema failure, version/name drift, missing/wrong OCI label and mutable image reference. Keep validation tools out of runtime dependencies.
4. Add the validator to PR CI and inspect the built image's config/labels. Keep the preview API probe manual/non-blocking; no login, publish, or Registry availability dependency in ordinary CI.
5. Docker `CMD`, Compose topology and entrypoints are unchanged. No Linux stdio entrypoint was added. Dockerfile creates non-writable, sentinel-only defaults for all 16 slots so the fixed registry scan treats unused slots as disabled; Compose's existing `.empty` bind behavior remains intact. The manifest omits `WORKDIR_01_PATH`, since the container path is selected by the bind mount and `main` does not consume that variable. OCI + Streamable HTTP Registry client interoperability remains unverified.

## Suggested gates

- Offline validator: valid manifest; unknown/invalid transport; malformed URL; forbidden mutable-only tag; server-name/image-label mismatch; project/manifest/OCI tag mismatch; secret/host-specific path rejection.
- Container gate: build a scratch-tag image and inspect config/OCI labels; confirm default command remains HTTP and that port 8000 plus `/mcp` are accurate.
- Existing root/Compose gates listed in `docs/maintainers/workflow.md` for Dockerfile/Compose changes. For a docs/manifest-only change, run the focused offline validator and `git diff --check`.
- Optional maintainer probe: call official `/v0.1/validate` without credentials only after confirming this is allowed; record response, auth behavior and date. Separately test a real target Registry consumer launching the OCI package with the declared fixed port and URL. Neither is a publish operation.
