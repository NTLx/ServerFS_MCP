## 2. Frozen Phase A contract fixture

[`v022_diagnostic_catalog_v1.json`](../agent_bridge/benchmarks/fixtures/v022_diagnostic_catalog_v1.json) is the maintainer-only machine-readable catalog fixture. Its JSON examples deliberately contain no IDs, paths, prompts, model/session identifiers, provider text or arbitrary metadata. The governing semantics and complete JSON envelopes remain those in `dev_plan_v0.22.md` §§4–9.

Frozen values recorded for implementation:

- Catalog version: `1`.
- Operations: `agent.queue_wait`, `agent.lease_acquire`, `agent.runtime_start`, `agent.execution`, `agent.waiting_external`, `agent.finalization`; `agent.task` is summary-only; `agent.recovery` may form an independent post-restart trace.
- Runtime family: `codex`, `claude`, `qoder`, `acp`, `unknown`.
- Task terminal outcomes: existing task vocabulary `succeeded`, `failed`, `cancelled`, `interrupted`; seal reason mapping is respectively `ok`, `degraded`, `safe`, `unavailable`.
- Completeness: `complete`, `truncated_prefix`, `restarted`, `restarted_truncated_prefix`.
- Query dispositions: `available`, `unknown_task`, `not_retained`, `bridge_unavailable`. Bounded not-retained reasons may be `evicted`, `bridge_restarted`, `capacity_exhausted`, `recording_unavailable`; do not guess an unestablished reason.
- Buffer ceilings: 2,048 global retained records; 1,048,576 logical UTF-8 JSON payload bytes; 64 total records/task including one seal (at most 63 ordinary); 32,768 bytes/task including seal reservation; 1,024 bytes/ordinary operation; 512 bytes reserved for terminal seal.
- Timing: diagnostic wall clock is Bridge-local monotonic submit staging through terminal transition; accounted is retained leaf durations only; active execution sums `agent.execution`; external wait sums `agent.waiting_external`; lease wait sums only `acquired` lease operations; unaccounted is wall clock minus accounted and may be negative. `busy` is not lease wait latency.
- Identity and ownership: Bridge-generated, Bridge-local and memory-only; no Core-to-Bridge diagnostic identity; no persistence/export; task ID is only the local task-query key/output identity.

The Phase A fixture is a schema/benchmark input, not executable recorder code. The future deterministic harness should consume preconstructed fixture records for record, seal, whole-task eviction, saturated snapshot and maximum-size task projection cases, with no filesystem/provider/network activity. That harness and all implementation-specific microbench measurements remain later work because no recorder exists in Phase A.

## 3. Fresh Linux/VPS pre-v0.22 baseline

Host: `VPS001`, Linux `6.8.0-136-generic`, x86_64, Python `3.12.13`; source revision `3ec4389f24e04a954a150ea1b1d5939bacaf35f2`. This was run before any v0.22 source instrumentation. The existing v0.21 benchmark was executed three independent times from `agent_bridge/`:

```bash

  --startup-iterations 20 --task-iterations 100 \
  --lease-iterations 1000 --contention-iterations 100 \
```

Run-to-run task timing and lease outliers are visible. Preserve the individual runs as the comparison evidence; the cross-run median rule follows the v0.21 benchmark shape and does not imply host variance is absent. The fresh submit-call baseline median is 25.112 ms; Phase E compares the same workload and computes the allowed +5.0 ms against this value. No v0.22 performance claim is made by Phase A.

Recorder-independent timing observation: the benchmark’s persisted `created_at → started_at` and `started_at → completed_at` distributions are wall-clock durable lifecycle durations, while the submit-call timer surrounds `submit_task()` and lease histograms surround `acquire_exclusive()`. They do not isolate monotonic phase durations or external human wait; the plan’s diagnostic phase definitions must be measured at the listed transition seams, not inferred by subtracting persisted timestamps.
