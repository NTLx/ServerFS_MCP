# ServerFS v0.21.0 Phase C — Structured Status & Operator Convergence

Status: **Phase C implementation complete; regression gate PASS.** This phase adds an opt-in, sanitized common projection to the existing native `serverfs service status` command on macOS and Windows. The default native status output is unchanged. No new network endpoint, MCP tool, listener, collector, dependency, persistent schema, repair action, or authority was added.

Baseline: Phase B commit `09f566f` (`feat: add v0.21 observation contract`).

Date: 2026-10-22.

## 1. Decision summary

Phase C uses the narrowest existing operator surface instead of creating a second status service:

```text
serverfs service status                         # existing native detail, unchanged
serverfs service status --format common-json   # sanitized common projection
serverfs service status --format common-human  # same semantics, human rendering
```

The new projection is intentionally opt-in. `native` remains the default so existing scripts and operators retain the exact platform-specific lifecycle information they already use.

The common projection is a **summary**, not a replacement for platform-native status, `serverfs doctor`, Tunnel deep diagnostics, or the host-observability publication recipe.

## 2. Implemented files

- `src/serverfs_mcp/service_observability.py`
  - pure Windows/macOS status adapters;
  - common JSON document renderer;
  - common human renderer;
  - no I/O other than serialization of already-returned mappings.
- `src/serverfs_mcp/cli.py`
  - adds `--format native|common-json|common-human` only to `service status`;
  - default remains `native`;
  - common output stays on stderr, matching the existing command channel.
- `tests/test_service_observability.py`
  - platform mapping, aggregation, redaction, renderer parity and actual CLI-path compatibility tests.

## 3. Compatibility contract

### 3.1 Default output is unchanged

`serverfs service status` without `--format` still calls the platform-native status implementation exactly once and writes the existing sorted native JSON document to stderr.

Direct internal/test calls that provide a `SimpleNamespace` without the new `status_format` attribute also fall back to `native` through `getattr(..., "native")`. This preserves existing direct-call test and compatibility behavior.

No existing command, exit code, MCP schema, MCP response, service-manager implementation, lifecycle primitive, state file, Task Scheduler contract, ServiceManagement registration, or Tunnel behavior changed.

### 3.2 Common output is deliberately smaller

`common-json` and `common-human` contain only the bounded v0.21 observation vocabulary:

- process role and platform family;
- separate liveness, readiness and health aggregate states/reasons;
- bounded component applicability, health, provenance and reason.

They do **not** contain native task names, PIDs, executable paths, state/log paths, raw service-manager state strings, scheduler details, arbitrary error strings, URLs, credentials, environment values, task/session/provider identifiers or workdir identities.

The native output remains available when those platform-specific operational details are needed.

## 4. Windows mapping

The Windows adapter projects only facts already returned by `windows_service.status()`.

### Recovery/lifecycle component

The `recovery` component represents the managed Task Scheduler/watchdog/runner lifecycle:

| Native evidence | Common state |
|---|---|
| task explicitly not registered | `unavailable / observed / not_ready` |
| registration query unavailable | `unknown / observed / probe_failed` |
| manifest missing or registered task invalid | `unavailable / observed / invalid_configuration` |
| watchdog alive + runner alive | `healthy / observed / ok` |
| watchdog alive + runner absent + unclean-exit evidence | `degraded / observed / degraded` |
| watchdog alive + runner absent without unclean-exit evidence | `unavailable / observed / not_ready` |
| watchdog not alive | `unavailable / observed / unavailable` |

Liveness requires this component only. This prevents an optional/remote Tunnel condition from turning a still-running local supervisor into a false liveness failure.

### Tunnel component

Tunnel state is derived only when the current managed runner gives lifecycle evidence:

- runner not alive → `unknown / not_checked / configured_not_checked`;
- runner alive and `last_tunnel_started_at` is newer than any exit → `healthy / observed / ok`;
- runner alive and a Tunnel exit is at least as new as the start → `unavailable / observed / unavailable`;
- otherwise → `unknown / not_checked / configured_not_checked`.

Readiness and health require both the recovery/lifecycle component and Tunnel. This means registration/configuration alone cannot become readiness.

The projection does not query Tunnel, provider or control plane and does not cause a restart.

## 5. macOS mapping

The macOS adapter projects only the managed Tunnel lifecycle evidence already present in `darwin_service.status()`.

- invalid bundle → `unavailable / observed / invalid_configuration`;
- positive managed Tunnel PID → `healthy / observed / ok`;
- positive managed Tunnel PID plus unmanaged Tunnel process evidence → `degraded / observed / degraded`;
- no managed Tunnel PID with `not-installed`, `not-registered`, `not-found` or `requires-approval` → `unavailable / observed / not_ready`;
- `invalid-bundle` service state → `unavailable / observed / invalid_configuration`;
- any other no-PID state → `unknown / observed / unknown_value`.

Liveness, readiness and health all require the Tunnel component for the native-service role.

The common macOS projection deliberately does **not** infer Agent Bridge applicability merely because the Service Manager exposes an `agent-bridge` service name. This status surface by itself cannot safely distinguish “operator intentionally disabled Agent Bridge” from “Agent Bridge expected but not registered”. That applicability remains in configuration/doctor-specific evidence rather than being guessed into common health.

## 6. Human/JSON parity

Both common renderers use the same `ObservationSnapshot` and `RolePolicy` and call the same aggregate function for liveness/readiness/health.

Synthetic common-human shape:

```text
role: native_service
platform: darwin
liveness: healthy (all_required_healthy)
readiness: healthy (all_required_healthy)
health: healthy (all_required_healthy)
tunnel: enabled healthy observed (ok)
```

The common JSON contains the same snapshot plus `liveness`, `readiness`, and `health` aggregate dictionaries. Tests compare renderer results directly against the shared aggregation result.

Both formats are written to stderr, consistent with the existing native service-status command. stdout remains empty.

## 7. Relationship to doctor, Tunnel diagnostics and host observability

### `serverfs doctor`

Doctor remains an explicit read-only configuration/platform diagnostic. Its existing `OK` / `WARN` / `FAIL` lines cover filesystem, configuration, backend, Agent/private-state, local proxy and related checks. Phase C does not reinterpret those free-form diagnostics as metric labels and does not silently change their output/exit-code contract.

The semantic convergence is therefore deliberate rather than destructive:

- common status answers bounded lifecycle liveness/readiness/health from evidence the native service status can prove;
- doctor answers deeper local configuration/safety questions;
- `OK`/`WARN`/`FAIL` are not aliases for common `healthy`/`degraded`/`unavailable`.

A future adapter may reuse more doctor facts only if each fact is mapped explicitly into bounded component/reason vocabulary without copying free-form detail.

### Tunnel diagnostics

The native common projection is a lifecycle summary only. It does not replace Tunnel `/health/...` component diagnostics or prove control-plane polling, MCP observation, response delivery, queue or dispatcher state unless that exact evidence exists in the native status mapping.

Windows uses only managed runner/Tunnel-generation evidence. macOS uses only managed Tunnel process evidence. If the native lifecycle mapping cannot prove current Tunnel health, the common state remains `unknown`.

Linux Compose deployments keep using the Tunnel's existing private health interface and Compose diagnostics. Phase C does **not** invent a `native_service` projection for Linux where the corresponding native service-manager surface does not exist.

### Read-only host observability

The host-observability recipe remains an operator-owned external publication channel:

```text
host collector -> sanitized snapshot directory -> read-only ServerFS workdir
```

Those generated files are not reclassified as intrinsic ServerFS health. Collection authority remains outside ServerFS core and no shell/Docker authority is added.

## 8. Public documentation timing

The new CLI behavior is implemented on the unreleased v0.21 development line. Public English/Simplified-Chinese site pages remain at the current stable-release wording during Phase C so they do not advertise an unreleased command as stable functionality.

Release-facing site and README updates are intentionally deferred to **Phase F**, where both locales, native platform evidence, site build and stale-current-state claims are reviewed together.
