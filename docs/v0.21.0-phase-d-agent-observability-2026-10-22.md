## 1. Implemented scope

Phase D adds bounded, process-local Agent Bridge observations in:

- `agent_bridge/src/serverfs_agent_bridge/observability.py`;
- `agent_bridge/src/serverfs_agent_bridge/service.py`;
- `agent_bridge/tests/test_observability.py`.

The implementation is deliberately Bridge-local. The independently packaged Agent Bridge does **not** import `serverfs_mcp`; instead its tests pin the exact v0.21 Phase B Agent metric names and closed label domains so drift is explicit.

No exporter, listener, RPC method, network egress, background observer, persistent metric table, provider call, new dependency, log sink, or ordinary MCP/filesystem request-path instrumentation was added.

## 2. In-memory metric model

The Bridge implements the Phase B Agent subset exactly:

- `serverfs_agent_tasks_total`;
- `serverfs_agent_task_duration_seconds`;
- `serverfs_agent_queue_depth`;
- `serverfs_agent_queue_wait_seconds`;
- `serverfs_agent_lease_acquisitions_total`;
- `serverfs_agent_lease_wait_seconds`;
- `serverfs_agent_recovery_total`.

All labels are closed finite domains. Runtime identity is normalized to `codex`, `claude`, `qoder`, `acp`, or `unknown`; all ACP profile names collapse to `acp`, and the deterministic test runtime `fake` becomes `unknown` rather than becoming a production label.

The complete Bridge-local catalog has a theoretical maximum of **416 series**. Module import fails if the catalog exceeds the frozen 10,000-series ceiling.

Counters store only integer totals keyed by metric name plus bounded labels. Histogram observations store only `count`, `sum`, `min`, and `max`; they do not retain a sample list or task history. This keeps memory bounded by the catalog cross-product rather than workload/task count.

## 3. Task lifecycle accounting

Terminal metrics are recorded from the durable task record **after** an existing terminal transition succeeds. A single helper wraps terminal transitions across shutdown, cancellation, interaction timeout, startup recovery, scheduling failure, success, provider failure, cancellation and interruption paths.

The helper first checks whether the task is already terminal, so repeated cleanup cannot double-count a terminal result. It reuses the `TaskRecord` returned by `TaskStore.transition_task()` rather than issuing a second database read.

Observation failure is explicitly non-authoritative: a bounded metric validation `TypeError`/`ValueError` after the durable transition is swallowed, and a deterministic test proves the task still reaches `succeeded` with its final response intact. Observability therefore cannot reverse or block a business state transition.

For terminal records:

- outcome uses the existing terminal vocabulary `succeeded|failed|cancelled|interrupted`;
- task execution duration is durable `started_at -> completed_at`;
- queue wait is durable `created_at -> started_at`;
- missing, malformed, negative, or otherwise unusable timestamp pairs omit only the dependent timing observation; terminal outcome accounting still occurs.

Task IDs, workdir aliases/paths, requested models, correlation/idempotency IDs, provider/native session IDs, prompts, results, and error text are never used as metric labels or retained in metric rows.

## 4. Queue depth

Queue depth is derived only when `observability_snapshot()` is called; there is no polling loop.

The snapshot uses the existing bounded `store.list_nonterminal_tasks()` view:

- `QUEUED` -> `runnable`;
- `WAITING_FOR_APPROVAL` / `WAITING_FOR_QUESTION` -> `waiting_interaction`;
- `STARTING` / `RUNNING` are not queue depth.

Zero rows are emitted only for configured bounded runtime families. Multiple ACP profiles collapse to a single `acp` family. No arbitrary runtime/profile identity is exposed.

`observability_snapshot()` remains an **internal BridgeService method** in Phase D; it is not added to the public Bridge RPC protocol.

## 5. Writer lease observations

The existing `LeaseManager` and its platform lock primitives are unchanged.

`BridgeService.submit_task()` measures only the existing nonblocking `acquire_exclusive()` call using `time.perf_counter()`:

- success -> `acquired`;
- existing `WORKDIR_BUSY` -> `busy`;
- any other acquisition exception -> `failure`.

The original exception behavior is preserved. Review-mode tasks that do not acquire a writer lease emit no writer-lease observation.

Tests verify that real writer contention still raises the existing `WORKDIR_BUSY` error and is counted without changing the lease boundary.

## 6. Recovery / guard observations

Recovery observations describe existing decisions; they do not make those decisions.

### Guard reconciliation

- provider proven inactive, existing guard cleared -> `guard / success / ok`;
- provider still active, existing refusal retained -> `guard / unknown / recovery_guard`;
- stop cannot be proven, existing refusal retained -> `guard / unknown / stop_unproven`;
- invalid/orphaned guard state -> `guard / failure / invalid_configuration`.

Tests explicitly verify the original guard semantics: inactive evidence clears the guard, while active/unknown stop evidence keeps the guard and preserves `WORKDIR_RECOVERY_REQUIRED`.

### Startup reconciliation

- successful reattachment -> `resume / success / ok`;
- tasks moved to `INTERRUPTED` record the terminal task outcome plus an `interrupt` recovery result based on the already-computed effective provider-active evidence;
- recovery metrics never override the existing adapter result or supervisor containment proof.

### Task-finally guard decision

When existing task cleanup cannot immediately clear a guard, the existing reconciliation result is mapped to bounded `ok`, `recovery_guard`, `stop_unproven`, or `probe_failed` evidence. The pre-existing `clear_guard` decision remains the authority.

## 7. Redaction and cardinality evidence

The focused tests freeze exact label names and exact allowed domains for all seven Agent metric families and assert the 416-series ceiling.

Sentinel task ID, workdir identity, requested model, correlation ID, and arbitrary error text are inserted into synthetic task records; none appears anywhere in `json.dumps(observability_snapshot())`.

The snapshot contains only schema version, metric name/type/unit, closed labels, bounded counter/gauge values, and aggregate timing summary values.

## 10. Performance gate verdict

Hard budgets frozen before instrumentation:

1. **No background observer loop/thread/timer — PASS.** Observation updates only at existing lifecycle transitions; queue depth is snapshot-derived.
2. **Startup RSS observation increment <=256 KiB — PASS.** After median delta is 0 KiB.
3. **No continuing idle RSS growth — PASS.** After median idle delta is 0 KiB.
4. **Submit-call cross-run median p95 <=22.424 ms — PASS.** Measured 21.409 ms.
5. **Lease primitive unchanged — PASS structurally.** `LeaseManager` is unmodified; standalone lease p95 improved from 0.105 ms to 0.0887 ms median within host noise.
6. **Ordinary filesystem MCP request path untouched — PASS structurally.** Phase D changes are confined to Agent Bridge files and add no root MCP hot-path instrumentation.

Submit-to-terminal and durable queue/execution timings increased modestly in the cross-run median but remain diagnostic rather than hard thresholds because the baseline itself showed substantial host/cache variation. No hard performance budget failed.

## 11. Platform scope and known limits

The before/after performance evidence is Linux/VPS only. macOS/Windows native performance remains **Not verified** until Phase F reruns the same benchmark shape where those native Bridge environments are available.

The in-memory metrics are process-local and reset on Bridge restart. They are operational observations, not audit records. No exporter or public metrics API exists yet.

## 12. Phase D gate verdict

**PASS.** Agent task outcomes, durable queue/execution timing, snapshot queue depth, writer-lease acquisition/contention and recovery/guard outcomes are represented with bounded, redacted, process-local metrics. Existing task/lease/recovery authority semantics are preserved, functional regressions are green except for one A/B-proven baseline timeout, and all frozen Linux/VPS performance budgets pass.
