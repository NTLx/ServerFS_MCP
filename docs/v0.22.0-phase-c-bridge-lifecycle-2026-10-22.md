# ServerFS v0.22.0 Phase C — Bridge Lifecycle Instrumentation

Status: **Phase C complete; Phase D and later surfaces are not started.**

Date: 2026-10-22. Phase C wires the Phase B in-memory recorder into the existing
`BridgeService` lifecycle. No RPC/CLI/MCP surface, provider adapter, SQLite schema,
dependency, exporter, configuration, release version or site file changed.

## 1. Lifecycle evidence delivered

- Submission staging is created only after the in-lock idempotency recheck misses. The
  recorder slot is admitted only after durable `create_task()` succeeds. Idempotent
  retries do not reopen or append to the original slot.
- Lease metric and diagnostic durations share the same `lease_ended` sample and the
  existing `acquired` / `busy` / `failure` classification. Busy attempts are not
  counted in the recorder's acquired-only lease-wait rollup.
- Queue wait, Bridge-owned `runtime_start`, and execution segments are recorded from
  Bridge-observable boundaries. Runtime start ends and execution starts at one shared
  monotonic boundary. Provider completion uses one shared boundary for execution end
  and finalization start.
- Approval/question wait starts only after `create_pending_request()` durably commits
  the waiting state. It ends immediately after successful `resolve_request()` commits
  RUNNING, or at the terminal transition boundary. Resume execution starts only when
  `_wait_for_request()` returns to the provider coroutine, leaving the scheduler gap
  unaccounted. Approval advice is outside the external-wait interval.
- Successful result finalization measures Bridge-owned result validation, redaction,
  hashing and spool preparation before the terminal transition. Failure paths do not
  invent a finalization start.
- `_transition_terminal()` captures one monotonic boundary, commits the durable state
  first, records any open execution/wait segment against that captured boundary,
  projects the existing metric, and seals with the same `completed_at`. Ordinary
  `Exception` from metric/diagnostic projection is isolated; `BaseException` is not
  caught. Terminal status, metric outcome and seal outcome share the store transition.
- Startup reconciliation admits only a durable preexisting nonterminal task observed
  in this Bridge generation with `restarted` completeness and a bounded
  `agent.recovery` observation. No prior phases or identities are reconstructed.
- Startup reconciliation of an orphaned durable guard also records a restarted
  `agent.recovery` observation for the associated task when that durable task is found.
  Ordinary in-process guard checks do not claim restarted completeness.
- Service-side per-task timing/sequence maps are cleared after terminal sealing. A
  rejected/failed recording does not advance the sequence. Recorder slot retention
  remains independent and bounded by the Phase B recorder.
- `agent.recovery` uses the existing `RECOVERY_OUTCOMES` vocabulary. The catalog
  fixture and contract test now state this domain explicitly.

## 2. Focused contract coverage

`agent_bridge/tests/test_service.py` and `test_diagnostics.py` cover successful terminal
metric/seal parity, provider failure, cancellation during execution and external wait,
interaction timeout, repeated approval rounds, question waits, exact adjacent phase
boundaries, terminal-seal boundary, idempotent retry, 30 sequential terminal tasks with
empty helper maps, 1,000 rejected-record attempts without sequence growth, startup
reconciliation of a real preexisting durable task, injected `RuntimeError` projection
failures, recovery vocabulary parity, and diagnostic-ID exclusion from provider
context, task/events/results/manifest and durable SQLite files.

The existing approval-advisor path remains before durable wait entry; its time is not
classified as human wait. The existing task, lease, cancellation and recovery decisions
remain authoritative.
