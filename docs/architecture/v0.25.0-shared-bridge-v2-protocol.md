# ADR Draft v0.25.0 — Shared Bridge v2 Client Authorization

> Historical rejected protocol experiment. The reconciliation record cited below describes a later source-parity investigation, not a current requirement to share private wire formats. The [native-first ADR](v0.25.0-native-platform-boundaries.md) governs implementation choices; use actual version-matched platform runbooks and code for today's grant protocol, limits, replay defense and task submission semantics. In particular, the experimental idempotency and rotation proposals below are not current signed-v2 capabilities.

Status: SUPERSEDED EXPERIMENTAL DRAFT — NOT THE v0.25.0 IMPLEMENTATION CONTRACT.
Use docs/architecture/v0.25.0-bridge-v2-macos-windows-reconciliation.md
and the inspected Windows core_grants.py contract for all further v2 work.
Date: 2026-11-14.
Scope: Linux, macOS and Windows. No runtime behavior is changed by this document.

## 1. Problem and current boundary

The accepted instance model allows a Core to use bridge_mode=disabled, owned, or shared.
Owned and disabled have completed isolated macOS lifecycle acceptance. Shared MUST NOT
be enabled merely by pointing two same-user Cores at one socket or named pipe.

The current Bridge protocol is version 1: newline-delimited JSON RPC with the four
request fields protocol_version, request_id, method, params. The local endpoint
checks Linux SO_PEERCRED, macOS getpeereid or the measured Windows pipe client SID.
These checks establish an OS user, not a unique Core identity. Bridge workdir
policies and task-state access are not yet partitioned by an authenticated Core.
Therefore v1 does not authorize two independent Cores on one Bridge.

## 2. Decision proposed for v2

Keep the existing local IPC transport, Bridge process and bounded JSON-lines framing.
Add a per-Core authenticated envelope and a Bridge-owned registry of explicit client
grants. Do not introduce a central instance registry or another supervisor.

Each shared Core receives a distinct 256-bit random secret through an owner-approved
private-file provisioning step. The Bridge owner stores the corresponding grant;
the Core cannot create, expand or revoke its own grant. HMAC-SHA256 authenticates
each request, including its exact request bytes and intended Bridge.

Proposed wire shape (values illustrative, not deployed):

~~~json
{
  "protocol_version": 2,
  "bridge_id": "shared-one",
  "core_id": "core-blue",
  "grant_id": "grant-blue-1",
  "issued_at_ms": 1794672000000,
  "nonce_b64": "<base64url of 16 fresh random bytes>",
  "payload_b64": "<base64url of UTF-8 JSON request>",
  "mac_b64": "<base64url of HMAC-SHA256>"
}
~~~

Decoded payload is an exact object with request_id, method and params.
No additional top-level fields, unknown fields, duplicate JSON object keys,
NaN, Infinity, invalid UTF-8 or oversized payloads are accepted. Do not parse
or dispatch the payload until the outer envelope, authenticated peer and HMAC
have passed.

Compute the MAC over domain-separated length-prefixed UTF-8/byte fields in
the fixed order: protocol label "serverfs-bridge-v2", bridge_id, core_id,
grant_id, issued_at_ms as canonical decimal ASCII, decoded nonce bytes,
decoded payload bytes. Every variable field uses an unsigned 32-bit big-endian
length prefix. This avoids JSON canonicalization and delimiter ambiguity.
All base64url fields require one canonical unpadded spelling; compare MAC tags
in constant time. Exact MAC encoding will be frozen by cross-platform test
vectors before implementation.

Recommended initial bounds (must be fixed in tests): decoded request at most
1 MiB, nonce exactly 16 bytes, secret exactly 32 bytes, clock skew at most
30 seconds, request age at most 60 seconds. Do not allow unknown algorithms
or selectable hash functions in client input.

## 3. Authorization sequence and replay protection

The Bridge performs these checks in order, before ANY task/repo operation:

1. Measure and authorize the local IPC peer using the existing UID/GID/SID gate.
2. Parse the bounded, exact v2 envelope; verify bridge_id equals this Bridge.
3. Resolve (core_id, grant_id) in the Bridge owner's active grant registry.
4. Verify active grant validity window, non-revocation and HMAC in constant time.
5. Check timestamp freshness and atomically record (grant_id, nonce) as unused.
6. Resolve the current policy revision and authorized Core-specific capabilities.
7. Decode and validate request payload; authorize the method and any workdir/task.
8. Dispatch the method with an immutable authenticated ClientContext.

Replay nonces MUST be inserted with a unique constraint in a durable Bridge-owned
ledger (existing SQLite store is a candidate), not only a process-local cache:
restart must not reopen a replay window. Expired entries may be pruned in bounded
batches after expiry. Invalid MAC requests never consume nonce ledger entries.
Failure to write/check the replay ledger is fail-closed, not best-effort.

A duplicate nonce is rejected even when request_id differs. Reusing the same
logical idempotency key with a NEW nonce follows the existing application-level
idempotency semantics; transport replay and task idempotency are separate.

## 4. Grant and workdir policy

An owner-controlled grant binds:
- bridge_id, core_id, grant_id, key-file reference, enabled/revoked status,
  not_before/not_after and monotonic policy revision;
- exact allowed workdir aliases and canonical host roots;
- per-alias read-only/write, Agent runtime, mode, Repo Ops and operation limits;
- optional per-method denies and maximum task/queue limits.

The Bridge authorizes aliases and operations from its OWN current registry,
never by trusting an alias/root/policy digest supplied by the Core. A supplied
policy digest is only an equality guard against an owner-computed revision.
The Core performs its own ingress authorization and workdir checks too.

Initial v2 scope: enforce globally unique workdir aliases among shared Cores,
and reject overlapping canonical writable roots across different Bridges.
This deliberately defers per-Core alias namespace remapping and cross-Bridge
writer lease coordination. If the two proposed Core policies require either
feature, refuse shared attachment rather than weakening writer isolation.

The owner stores grants and key files under private, symlink-free paths with
restricted user ownership and permissions (directories 0700, files 0600);
no secrets, raw MACs or full private config documents go to logs or RPC errors.
A Core never has write access to the Bridge owner registry.

## 5. Task ownership is mandatory

Every task, event, approval, cancellation and result created by a v2 client
must be bound to the authenticated core_id and grant identity at submission.
Subsequent get/list/read/respond/cancel/stream calls must reauthorize that
same Core against current owner policy, including after process restart.
A guessed task_id cannot cross client boundaries.

The existing task store must gain a checked Core owner field and migration
before shared mode can be enabled. Unknown/legacy-owner task rows are not
readable through shared-v2 clients. Diagnostics, runtime discovery, Repo Ops
and administrative methods need an explicit per-method permission matrix;
global Bridge diagnostics are owner-only unless specifically redacted.

## 6. Rotation, revoke, lifecycle and compatibility

Provisioning or rotating grants is an explicit Bridge-owner operation with
revision/CAS checks. Rotation issues a new grant_id and secret; old and new
may overlap for a bounded owner-defined interval. Revocation immediately
rejects future requests and must define whether in-flight tasks are cancelled,
drained or remain visible to the owning Core. No silent privilege expansion.

A shared Core may attach/detach its own client binding but MUST NOT stop,
restart, upgrade, uninstall, or remove its referenced Bridge. A Bridge owner
must reject deletion while registered clients or owned tasks remain unless
a journaled detach/migration completes.

Protocol v1 stays unchanged for existing default and exclusive owned
Bridges. A shared Bridge MUST reject v1 requests entirely: allowing them on
the same endpoint would bypass v2 Core identification. A Bridge can advertise
v2 capability out of band, but must not automatically downgrade a shared
Core to v1 on authentication failure. Disabled/file-only never requests a
Bridge credential.

No production enablement, credential provisioning, service registration or
Git release action is authorized by this draft.

## 7. Implementation order and acceptance gates

A. Freeze the envelope, MAC vector, duplicate-key handling, bounds, replay
   ledger behavior and error vocabulary as pure cross-platform tests.
B. Introduce a verified owner grant registry and immutable ClientContext.
C. Add v2 Bridge verification and owner-only grant lifecycle; keep v1 intact.
D. Enforce Core owner and method/workdir policy on all Bridge RPCs and task
   store reads/writes, including cancellation, approvals and streaming.
E. Add v2 client signing and shared Core binding on Linux, Windows and macOS.
F. Test two Cores with distinct policies and one shared Bridge; prove task,
   file, Repo Ops and approval isolation, revoke/rotate and restart behavior,
   replay rejection and no default PID changes.
G. Only after the three-platform matrix passes, conduct isolated runtime
   operational acceptance. Real public ingress is a separate gate.

Mandatory negative tests: forged core_id, revoked/stale grant, swapped
bridge_id, payload tampering, wrong policy revision, replay before/after
restart, cross-Core task_id, alias collision, overlapping writer root,
v1 downgrade on shared Bridge, symlinked key, bad file permissions,
unknown JSON fields, malformed base64, oversized frame, and failure to
persist a nonce.

- agent_bridge/src/serverfs_agent_bridge/shared_v2_crypto.py
- agent_bridge/tests/test_shared_v2_crypto.py
- agent_bridge/src/serverfs_agent_bridge/shared_v2_replay.py
- agent_bridge/tests/test_shared_v2_replay.py
- agent_bridge/src/serverfs_agent_bridge/shared_v2_grants.py
- agent_bridge/tests/test_shared_v2_grants.py
- agent_bridge/src/serverfs_agent_bridge/shared_v2_owner_store.py
- agent_bridge/tests/test_shared_v2_owner_store.py
- agent_bridge/src/serverfs_agent_bridge/shared_v2_task_scope.py
- agent_bridge/tests/test_shared_v2_task_scope.py
- agent_bridge/tests/test_shared_v2_security_chain.py (synthetic two-Core composition)
- agent_bridge/src/serverfs_agent_bridge/store.py (opt-in v2 scoped task creation)

The v2 wire HMAC vector uses secret=000102...1f (32 bytes),
nonce=000102...0f (16 bytes), bridge_id shared-one, core_id
core-blue, grant_id grant-blue-1, issued_at_ms 1794672000000,
and exact payload bytes:
~~~
{"method":"bridge.ping","params":{},"request_id":"req-1"}
~~~
The fixed HMAC-SHA256 digest in hexadecimal is
86a58bd7c9c305c13a3d92e992ff55aea8fdcc7e641cb8b308a0468e8e63fe89.
This vector MUST be independently verified by Windows/Linux before freezing
the shared protocol.

The SQLite helper uses an explicit owner-only schema installation and
BEGIN IMMEDIATE + unique (grant_id, nonce) INSERT + successful COMMIT
before returning a claim. Checked request age is at most 60 seconds;
nonce records expire at issued_at_ms + 60000 and are pruned only when
expires_at_ms is strictly less than now. Missing table, locked database,
nested transaction or uncertain commit fails closed. The helper receives
an already MAC-verified envelope and a dedicated existing SQLite connection.

Two integration blockers remain even after successful local unit tests:
1. Bridge v1 currently caps incoming frames at 1 MiB; the v2 envelope
   expands a 1 MiB decoded payload to up to 1.5 MiB. Future v2 transport
   must admit its precise bound without weakening v1 framing, rejecting
   oversized input before decode.
2. The replay ledger is not yet wired into TaskStore or RPC dispatch.
   The new pure grant helper checks Bridge-bound Core/grant identity, owner
   policy revision, expiry/revocation, exact method/workdir allowlists and
   task-ID ownership AND original workdir scope through an explicit trusted
   Bridge-store callback. Same-Core tasks in revoked workdirs are denied;
   cross-workdir task continuation is denied. A new source-only owner Grant
   SQLite registry now verifies owner-provisioned private 32-byte key files,
   registers exact Bridge/Core/Grant identities, rejects cross-Core alias
   collisions within one Bridge, and supports revision-guarded revocation.
   Another explicit v2 task-scope sidecar stores Core/workdir ownership in
   the SAME transaction as task creation; legacy task rows remain unowned.
   Its v2 idempotency index is unique per (bridge_id, core_id, key), while
   v1 retains the existing global index. The explicit schema upgrade handles
   older experimental v2 sidecars; none of this is auto-enabled.
   Neither schema is initialized on ordinary v1 startup. The live owner
   provisioning/admin interface, verified shared dispatcher, method-specific
   task authorization and all real v2 integration remain unbuilt.

Local evidence after task/workdir-scope hardening: crypto+replay+grants
completed 90 tests with exit 0; complete Agent Bridge pytest returned
557 passed / 134 skipped, exit 0. Target Ruff lint/format and git diff
checks returned exit 0. A separate Claude review was cancelled without
producing findings; no independent security-audit PASS is claimed. Windows ServerFS was
unreachable during this implementation, so the MAC vector and envelope
still await independent Windows/Linux agreement.

Storage evidence on macOS: initial owner registry scope 112 targeted tests
PASS; opt-in task scope plus legacy store 80 passed / 2 skipped; after adding
concurrent alias registration negative coverage, focused storage regression
43 passed / 2 skipped. All associated Ruff lint/format and Git diff checks
returned 0; full Agent Bridge tests returned exit 0 at each stage. These
figures cover different overlapping test groups and must not be summed.

Further source evidence: idempotency-focused regression 89 passed / 2 skipped,
full Bridge suite 602 passed / 134 skipped (exit 0). A synthetic two-Core
crypto + owner Grant + replay + task scope composition test then passed
140 targeted cases; full Bridge pytest returned exit 0 with 740 collected
and an unspecified skipped count. Relevant Ruff lint/format/diff checks
all returned 0. These overlapping sets are not additive.

Additional integration gates: the source-only v2 idempotency index is not
wired into live BridgeService submit/dedupe, so live Core-scoped retry
semantics remain unverified. Owner grants still lack per-workdir write/action/
runtime ceilings, and overlapping writable roots across different Bridges
require coordination. An immutable ClientContext is not a substitute for a
trusted authenticated dispatcher.

No v2 request currently reaches a Bridge execution path. Existing v1
production services remain unchanged; source-only tests do not authorize
shared-mode deployment or release.

## 9. Open review decisions before integration

- The Bridge SQLite schema and transaction boundary for nonce acceptance
  versus method dispatch, including crash/retry behavior.
- The minimum method capability set shared clients may request, especially
  Bridge-global diagnostics and runtime enumeration.
- The owner-initiated revocation policy for already-running Agent tasks.
- Whether the first release can require disjoint alias names per Core
  (recommended to minimize changes to the existing PolicyRegistry).
- A cross-platform file/key provisioning mechanism and its explicit
  administrator consent boundary.

This document is a proposal, not evidence that Bridge v2 has been built or
that topology B is accepted. Changes to the accepted instance-model ADR must
be reviewed after Windows/Linux maintainers validate this contract.
