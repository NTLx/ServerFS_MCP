# ADR v0.25.0 — Native-first Platform Boundaries

- Status: ACCEPTED DESIGN CLARIFICATION (2026-11-16).
- Scope: macOS, Windows and Linux implementations of ServerFS MCP.
- Supersedes: prescriptive requirements to share private Bridge implementation or byte-identical private IPC protocols in historical v0.25.0 integration notes. Their measured evidence is retained.

## Decision

**Prefer the operating system's native solution. Share code only when a concrete security, correctness, maintenance or interoperability benefit has been demonstrated.** A common release number and repository do not imply identical internal implementation.

The **behavioral contract** is common: the externally exposed MCP tool names and schemas, authorization/error semantics, revision-guarded filesystem mutations, read-only and capability defaults, workdir confinement, optional Agent/Repo Ops/binary features, immutable instance/connector/Bridge identities, and independence of Connector, Core and Bridge lifecycles. Each supported OS must pass its own real acceptance tests against these observable outcomes.

Bridge modes remain `disabled`, `owned` and `shared`. Shared means multiple Cores authorized against **a Bridge on the same host**. It does **not** mean a Core on Windows has to speak private IPC to a Bridge on macOS, nor require identical on-disk state or wire bytes across these platforms.

## Platform-specific implementation is explicitly permitted

| Boundary | macOS native preference | Windows native preference | Linux preference |
| --- | --- | --- | --- |
| Service lifecycle | Signed app-associated `SMAppService` and launchd LaunchAgents / KeepAlive | Current-user Task Scheduler, Windows Job Objects and guarded owner | Independent Compose projects; optional user systemd Bridge |
| Core–Bridge IPC | Darwin AF_UNIX with native peer checks and explicit Core grants | Named Pipe with SID checks and explicit Core grants | Unix sockets with peer credentials and explicit Core grants |
| Private state | Per-user Library roots, signed bundle identity, strict file modes | User-private application data, checked DACLs and task identity | Bind-mounted per-instance storage with native permissions |
| Crash/restart handling | launchd service generation recovery | Task/Job supervision | Container/systemd restart policies |

The implementations may use different serialization, HMAC canonicalization, nonce-ledger schema, TaskStore design and lifecycle state machines **provided that equivalent security and observable behavior are proven on each platform**. This permission is not a security waiver: a shared Bridge MUST authenticate unique Core identities beyond a shared UID/SID; grants are explicit and owner-controlled; replay, stale/revoked grants, cross-Core task access and unauthorized aliases MUST fail closed. A shared Bridge must not accept a v1 fallback that bypasses Core identity.

No central instance manager, privileged common supervisor or new abstraction layer is justified solely to make platform implementations look alike. Existing working common modules may remain when they already reduce risk; this decision does not demand their removal.

## Reuse decision gate

Before requiring cross-platform source or private-wire unification, identify at least one demonstrated benefit:

1. A real supported interoperability case that exchanges those private messages or durable state.
2. A measurable reduction in duplicated security-critical logic or defects without weakening OS-specific protections.
3. Small, pure and testable shared logic that does not own OS resources or complicate deployment.

Otherwise, share **contract tests and acceptance scenarios**, not the implementation. If a host uses a given Bridge implementation, its local Core clients and grants must match **that same host's actual private protocol**; two unrelated platform implementations need not match each other.

## v0.25.0 release impact

- macOS development focuses on signed native `SMAppService`, lifecycle independence, local IPC authorization, named instances, file-only mode, multi-Core isolation, KeepAlive, safe cleanup and real MCP ingress verification.
- Windows development independently chooses the appropriate native Scheduler/Job/Named Pipe implementation; Linux independently uses Compose/systemd patterns.
- Cross-platform release acceptance checks the same **public behavior, security invariants, topologies A/B/C/D and exact release SHA**, while building/testing the OS-specific artifacts separately.
- Do not block macOS on Windows-specific HMAC byte vectors, storage schema or implementation parity **without a documented interop requirement**.
- Do not change already measured historical facts in `v0.25.0-bridge-v2-macos-windows-reconciliation.md`; its old prescriptive source-convergence sequence is superseded by this ADR.
- Deployment to production, secret rotation and any Git commit, push, tag or publication remain separate explicit actions.

## Non-negotiable security and operational gates

- Each Core grants only the least permitted workdir/method scope. Per-Core authentication, replay protection, revocation and task ownership must withstand restarts and cross-Core probing.
- Shared Core lifecycle operations cannot start, kill, upgrade, uninstall or reconfigure the owner Bridge.
- Independent Connector restarts do not restart Core or Bridge; Core operations do not implicitly touch other instances.
- Native Login Item/Task Scheduler/Compose identity, credential storage, signing/ACL and rollback are tested using their supported OS mechanisms.
- Green source tests cannot substitute for real native registration, process recovery or public MCP E2E; record untested gates as NOT VERIFIED.

Decision applies prospectively to v0.25.0 development and release gate design, without changing existing production processes.
