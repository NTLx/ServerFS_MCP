# v0.25.0 — macOS Bridge v2 shared-grants 集成门禁

**日期：** 2026-11-14
**状态：** 2026-11-14 历史基线；2026-11-15 已执行更新见第 5 节。
**基线：** Mac owned 原生 SMAppService E2E 已通过，证据见 `docs/diagnostics/v0250-macos-owned-native-acceptance-2026-11-14.md`。Windows 同期正在并行开发 Bridge v2，不对其仓库做写操作。

## 1. 核查事实：不能直接将 macOS v1 owned 当作 shared

Mac 当前 Bridge 入口 `agent_bridge/src/serverfs_agent_bridge/protocol.py` 是 v1 JSON-lines，`PROTOCOL_VERSION=1`，顶层仅允许 `protocol_version/request_id/method/params`。Darwin 本机 IPC 以 UID/GID 授权；`src/serverfs_mcp/agent_client.py` 的 v1 Core 客户端没有按 Core ID 签名的请求。现有 `darwin_instance_owned_binding.py` 为单个 owned Core 验证绑定与 TOML，不负责多 Core grant 的身份鉴别和任务归属。

因此 **两个同 UID 的 Core 即使有访问某个共享 Unix socket 的权限，也不能构成“已授权的两个 Core”**；不得把多对一 `shared` 变成简单的 `bridge_id` 和 socket 重定向。此前的双 owned Bridge 和双 Core E2E 只证明相互独立，不能替代共享授权证明。

Windows 当前工作树 `docs/architecture/v0.25.0-bridge-v2-core-grants.md` 已明确 Bridge v2 的另一个协议边界（该文档已只读核对）：

- `core_grants_enabled=false` 为默认；v1 服务/公共 MCP 工具行为不变。v2 必须在**独立、非默认 Bridge 端点**显式启用；不对 v1 请求进行降级。
- Bridge owner 提供私有的 `state_dir/core-grants.json`，按 `schema_version=1` 与 `bridge_id` 固定；每个 Core 有 `core_id/key_id/32-byte HMAC secret`、受限方法和 workdir 以及完整策略 SHA-256。
- v2 请求需要 Core 身份签名、nonce 防重放、单个 Core/workdir 的可调用方法限制；任务持久记录 immutable owner，跨 Core 的 task/events/interaction 必须拒绝。
- grant 文件必须通过 owner 级私有权限与结构完整性校验，原子写入、显式轮换/撤销；启动不静默创建文件/密钥，运行中不自动热重载。
- Windows 已有隔离下真实 Named Pipe 两 Core 与 v2 Worker/Job 验收记录，但**尚非 Windows Task Scheduler 原生完整多 Core 验收**；不得将其解释成 Mac 的 v2 已集成。

以上属于当前两端真实代码与 ADR 已确认的差异；Mac 工作树尚未包含 Bridge v2 的 `core_grants_private.py`、HMAC signer、durable nonce/task owner 等公共实现，**不能在本机独立凭空重建一套第二协议**。

## 2. 合并策略（必须先对齐公共代码，再做 Mac 平台适配）

1. **冻结公共 v2 契约并确认版本源。** 等 Windows 的 v2 公共源码与测试完成可审查提交，先 diff 它对 `agent_bridge`、`src/serverfs_mcp`、公共 MCP tools 的精确修改；不要直接跨机覆盖正在编辑的文件。Mac owned 原生文件保留，Windows v2 已修复的任务 owner/nonce/capability 逻辑只保留一套。
2. **在 Mac 工作树隔离集成 v2 公共组件。** 统一 `core_grants_enabled` 默认 false、独立 v2 endpoint、HMAC Core signer、策略 SHA-256、密钥 ID、durable nonce replay store、immutable task Core owner；同一端点 v1 请求必须 fail closed。确保现有 owned v1 SMAppService、生产默认 v1 服务、文件型禁用 Bridge 模式回归。
3. **macOS Bridge v2 资源。** 复用 `instance_id/bridge_id`、签名 App/SMAppService、私有 0700/0600 状态和 Darwin Unix socket；v2 `core-grants.json` 由已认证的 Bridge owner 离线/原子发布。每个共享 Core 的私有 signing key 由 Core owner 单独存放；不能将所有 Core secret 集中给任何可读工作目录。
4. **macOS Core v2 client binding。** 为 `shared` Core 增加独立的受保护绑定（引用既有 `bridge_id`、授权 `core_id`、签名私钥文件、策略代次）；启动只验证合法 grant/owner 而**不注册、启动、停止、升级或卸载**共享 Bridge。Core 使用独立的 v2 签名客户端和公共工具 schema；Bridge 端必须以已认证 Core ID 决定 workdir 和任务可见性，不信任客户端声称的 alias/task id。
5. **撤销和轮换。** 在 Bridge 侧更新完整 grant 集，显式代次/原子替换；如果没有热重载，则只能在经 Bridge owner 控制的 restart 时生效。撤销之后旧 signer 的请求必须被拒绝，且不得残留可延续的会话能力。Bridge 不能在 active clients 存在时被共享 Core 停止或卸载。
6. **版本交叉验收：** 先源级/隔离服务，再真实 Mac 原生分离服务，再 Windows/Linux 共用 v2 回归；这些阶段均不能降低默认 v1 的既有安全验证。
