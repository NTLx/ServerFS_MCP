# ADR v0.27.0 — Platform Independence, Native-first Implementation

- Status: **ACCEPTED DESIGN** (2026-11-28; maintainer approved). Implementation and acceptance pending.
- Scope: Linux, macOS and Windows ServerFS product implementations, engineering boundaries and delivery.
- Supersedes prospectively: the permission to retain cross-platform product implementation in [v0.25.0 native-first boundaries](v0.25.0-native-platform-boundaries.md). Retains its native-first, security and behavioral requirements, the [instance model](v0.25.0-instance-model.md), lifecycle decoupling and [Linux ingress/host Bridge constraints](v0.25.0-linux-ingress-host-bridge.md).
- Execution plan: [v0.27.0 development plan](../plans/dev_plan_v0.27.0.md).
- Current released baseline remains v0.26.0 until independently accepted and authorized publication. This ADR is a target design, not a claim about installed systems.

## 1. Decision and rationale

**One product, one repository, three independent implementations. Share the public contract, not product runtime code.**

The shared Core, filesystem, Bridge, task store, provider adapters and platform seams in v0.26.0 create cross-platform change impact and constrain native choices. Independent implementation is a deliberate tradeoff: accept duplication and the obligation to audit fixes across all platforms in exchange for isolated engineering, native behavior and parallel development. Optimize local complexity and delivery independence, not total lines of code.

This is an architectural constraint, not an optional preference. No cross-platform ServerFS runtime library, common implementation package, symlink, relative import, source checkout dependency, copied-at-build shared runtime source or generation of runtime implementations from shared logic may reintroduce coupling. Platform-local reuse remains encouraged; upstream standard libraries, third-party SDKs and official MCP/ACP protocols are not prohibited. Similar independently maintained code is acceptable. No requirement to rewrite working code or change language/runtime in v0.27.0.

## 2. Ownership and repository boundary

Target layout (platform internals may differ):

```text
linux/           # self-contained product source, Bridge, Docker/Compose, configuration, dependencies, tests and deployment
macos/           # self-contained product source, Bridge, native Swift/service assets, configuration, dependencies, tests and deployment
windows/         # self-contained product source, Bridge, Win32/service assets, configuration, dependencies, tests and deployment
contracts/       # public schemas, behavioral/security specifications, test vectors and black-box conformance fixtures
docs/            # product ADRs, plans, maintainer guidance, release records
site/            # shared product website
skills/          # shared Host-facing operational skills and distribution
.github/         # platform-specific CI entry points and coordinated release
```

Each platform owns MCP Core, filesystem, binary transfer, applicable file ingress, authorization, Agent Bridge, provider adapters, task storage, Repo Ops, observability, MCP Apps/interaction assets, private IPC and lifecycle implementation. Each owns its manifests/lockfiles, packaging, installation, upgrade/uninstall scripts, platform docs and executable tests. Independent Core and Bridge environments within a platform remain valid.

A clean checkout containing only the platform subtree and declared external dependencies must suffice to build and run that product and its local tests; common contract/conformance checks may additionally consume the versioned contracts directory. Embed necessary platform-local build inputs and distribution metadata; no implicit dependency on repository root runtime files. Common website, skills, registry metadata and release tooling are product-level distribution concerns, never runtime dependencies. Keep package names, installation entry points, artifact identifiers and existing deployment compatibility where feasible; make necessary changes explicit and tested. Do not create three repositories or independent product release numbers.

## 3. Native implementation and runtime topology

| Boundary | Linux | macOS | Windows |
| --- | --- | --- | --- |
| Deployment | Independent Docker Compose Core/Connectors; direct HTTP optional | Native Apple Silicon / supported macOS, signed SMAppService and launchd | Native Windows 11 x64, current-user Task Scheduler and Job Objects |
| Bridge | Optional host-native user systemd; reuse installed host Agents | Native per-user owner and lifecycle | Native per-user owner and lifecycle; no WSL/VM |
| IPC | Unix socket, peer credentials and explicit signed grants | Darwin native IPC and explicit grants where signed-v2 applies | Named Pipe, SID/DACL and explicit signed grants where signed-v2 applies |
| Filesystem | Descriptor-relative POSIX traversal and verified atomic operations | Darwin/APFS native metadata and containment | NTFS HANDLE/reparse-point containment and native transaction protections |
| State | Private per-instance mounts/state and owner permissions | Private per-user Library roots and native identity | Private per-user application data and checked DACLs |

Maintain Connector/Core/Bridge lifecycle independence, immutable instance/Bridge/Connector identity, file-only mode and owned/shared/disabled Bridge modes. Shared Bridge is a same-host relationship, never an inter-platform private RPC requirement. Linux supports Cloudflare Tunnel, OpenAI Tunnel and direct HTTP independently; reverse proxy/TLS external configuration stays outside project responsibility where applicable. Do not force Bridge into Docker, expose Docker socket, create privileged supervisor or introduce a central instance manager.

Private IPC serialization, signing canonicalization, state schemas, configuration models, recovery and implementation languages can differ. Local matching Core and Bridge must be version-compatible and fail closed on mismatch. Public platform/provider support remains evidence-based, not inferred from identical schemas.

## 4. Common product contract

The common contract defines observable semantics and security rather than implementation. Freeze v0.26.0 behavior and measured capability matrix before migration; establish machine-readable public tool/resource schemas, stable errors, annotations, result schemas, task/event/approval semantics, protocol negotiation and optional capability declarations. Include auth, binary transfer, deterministic Repo Ops, instance identity and lifecycle, revision-guarded atomic mutations, read-only defaults, workdir confinement and provider-owned configuration. Maintain compatibility with both supported MCP protocol families (2025-11-25 and 2026-07-28), stdio and Streamable HTTP. Extensions require actual negotiation and client evidence; unsupported capabilities remain explicit.

Contract tests may use a common external black-box runner or shared data; they must not import product internals. The same public contract does not imply every optional feature, provider, or topology is supported everywhere. Publish a platform capability matrix and justify differences; do not regress existing supported behavior. New mandatory version outcomes must be demonstrated on every applicable platform.

## 5. Security boundaries (unchanged unless explicitly extended by approved plan)

The [maintainer invariants](../maintainers/invariants.md) remain binding. In particular:
- Preserve explicit grants, unique Core identity beyond UID/SID, nonce/replay defenses, revocation, per-workdir authorization, private approval identity, redaction and local audit. Never fall back to v1 to bypass v2 ownership.
- Apply path policy to all channels, preserve native race-resistant containment and metadata/atomicity contract. Do not broaden roots or expose arbitrary shell/argv/env.
- Preserve provider-native credentials, permission/sandbox policy, model selection, writer coordination, cancellation and persistent recovery guards. No unapproved native runtime admission; standard protocol first.
- Keep binary/file ingress isolated, Repo Ops deterministic, HTTP admission, Host/Origin and OAuth resource boundaries intact. No permission expansion merely to achieve parity or ease testing.
- All protocol/UI/notification adapters use the same authorized business operations. A UI, tool annotation, advisory model or event subscription never grants authority.
- An OS-specific fix triggers review of analogous defects on the other platforms, not automatic copying or shared implementation. Validate each applicable implementation independently.

## 6. Development, CI and release

First isolate implementations at v0.26.0 feature parity. Do not interleave mechanical migration with new features or speculative refactors. Establish and review the baseline and migration gate before starting the three parallel feature streams. Maintain a single integration branch; publish a clean split baseline only with explicit Git authorization. Platform branches own only their platform subtree; changes to contracts, product docs, distribution and CI/release coordination are centrally reviewed by the maintainer/ChatGPT. No incidental edits to another platform. Shared contract changes require an explicit proposal, compatible schema evolution and coordinated validation.

Use path-scoped independent platform CI for ordinary changes, with reliable required-check behavior even when a platform is unaffected; contract/release changes trigger relevant cross-platform checks. Release builds all applicable artifacts and checks all platform gates at the same integrated SHA, not three unrelated green commits. Keep artifact version identity, packaging, installer/runbook links, website and skills synchronized. Preserve existing upgrade/rollback state or provide explicit tested migration. Source tests are not substitutes for native lifecycle, real provider and authenticated ingress acceptance.

Acceptance of independence requires independent build contexts and local tests, import/build dependency checks, removal of obsolete root product source and cross-platform shims, independent CI/artifact verification and v0.26.0 behavioral/security parity. A change confined to one platform must not require editing/building another platform; release-wide checks still apply. No broad refactor beyond the split without an approved need.

## 7. Governance and non-goals

This ADR is durable from v0.27.0 onward; the versioned Plan governs delivery sequence and feature scope. Historical plans remain accurate records of their versions. Current deployment instructions describe measured released behavior, not prospective designs. If a current maintainer rule describes a pre-split layout, treat that as baseline until migration; update the affected instruction and executable validation together during the split. Conflicts in target design must be resolved by maintainer decision, not an Agent's convenience.

Non-goals: three separate repositories, central multi-host management, a cross-platform runtime SDK maintained by ServerFS, mandatory language rewrite, new privileged execution surfaces, forced wire/state parity, wholesale storage replacement, or expanding supported OS/runtime matrices without evidence and approval. NFS-specific support and post-publication Revision consistency remediation are deferred outside v0.27.0; existing local filesystem guarantees must not regress.
