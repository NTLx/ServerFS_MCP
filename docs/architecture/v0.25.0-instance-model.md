# ADR v0.25.0 — Instance Identity and Optional Bridge Sharing

- Status: ACCEPTED DESIGN, IMPLEMENTATION IN PROGRESS (2026-11-13).
- Scope: Linux Docker, macOS native, Windows native. This extends, and does not replace, `v0.25.0-lifecycle-decoupling.md`.
- Release: one v0.25.0 with real three-platform acceptance. Existing production services and their names remain unchanged until separately approved migrations.
- Native-first clarification (2026-11-16): `v0.25.0-native-platform-boundaries.md` governs implementation/reuse decisions. Shared identities and observable authorization behavior do **not** require byte-identical private Bridge IPC, HMAC serialization, state stores or lifecycle code across operating systems.

## 1. Decision

ServerFS comprises independently owned **ingress connectors**, **persistent HTTP MCP Core**, and optional **Agent Bridge**. An installation is identified by an immutable `instance_id`. The bridge has a separately identified `bridge_id`; a Core may use no Bridge, its own Bridge, or an explicitly shared existing Bridge. No central registry daemon, central orchestration service, global service manager, or second privileged supervisor is introduced.

These are distinct deployment topologies:

- A: multiple connectors -> one Core -> one Bridge.
- B: multiple independently configured Cores -> one shared Bridge.
- C: multiple independent Core/Bridge pairs, each with its own connectors.
- D: one or more file-only Cores without any Bridge.

Topology A is already partly deployed. Topologies B/C require implementation and dedicated acceptance; current same-SID/UID lock and authenticated IPC assumptions MUST NOT be bypassed to achieve them.

## 2. Identity and naming

The public control-plane identifier `instance_id` and private `bridge_id` are ASCII lowercase DNS-label-like slugs: 1–32 characters, initial and final character [a-z0-9], internal characters [a-z0-9-]. Reject whitespace, Unicode, uppercase aliases, separators, traversal, empty strings, and invalid identifiers before touching the OS. A connector can additionally carry a unique per-Core `connector_id` of the same grammar for multiple ingress instances of one provider.

The reserved **legacy/default** installation identifier `default` maps to current installed names and data roots. Existing Windows v25 fixed Task Scheduler names, existing macOS SMAppService labels and bundle identity, existing Linux Compose project and Linux Bridge systemd unit are not renamed or migrated implicitly. Non-default installations receive deterministic instance-qualified paths and OS service identifiers. Instances cannot claim an existing OS identity, socket, TCP listener, token path or writable state root. Do not infer ownership merely from matching a PID/name.

Proposed new install identities (implementation contracts, not a statement that installers support them yet):

| Resource | Legacy/default | New instance `staging` |
| --- | --- | --- |
| Windows task | `ServerFS v25 Core` | `ServerFS v25 staging Core` |
| Windows component data | `%LOCALAPPDATA%/ServerFS/v25/services/core` | `%LOCALAPPDATA%/ServerFS/v25/instances/staging/services/core` |
| macOS Core launch label | `com.ntlx.serverfs.http-origin` | `com.ntlx.serverfs.staging.core` |
| macOS private state | existing `ServerFS/service-manager` | `ServerFS/instances/staging/service-manager` |
| Linux Compose | preserve installed project | new `serverfs-staging` project |
| Linux Bridge unit | `serverfs-agent-bridge.service` | `serverfs-agent-bridge@staging.service` |

The name translation must be applied consistently to service registration, executable pinning, storage, manifests, process identity, readiness, stop/uninstall, log and private credential paths, rollback and tests. Do **not** enable a non-default instance merely by changing its task/LaunchAgent label: bridge IPC, lease, Job, socket and policy identity must also be distinct.

## 3. Bridge ownership / trust contracts

`bridge_mode` is one of `disabled`, `owned`, or `shared`. Disabled requires no Bridge ref and must keep file-only tools available. Owned requires an instance-private `bridge_id` and independent task/systemd/LaunchAgent ownership. Shared refers to an already managed Bridge and NEVER starts, stops, upgrades or uninstalls that Bridge when operating on the referencing Core. A Bridge owner must refuse deletion while active client registrations exist unless a journaled migration detaches them.

A Bridge accepting requests from multiple Cores MUST authenticate **each Core identity**, bind that identity to an explicit allowlisted workdir/policy capability, validate policy revisions, and reject unknown/stale/revoked clients. Same UID/SID, network reachability or a shared socket alone does not establish which Core is calling or grant access. Existing single-Core fingerprints are insufficient for two independently configured policies; either extend the authorization model with per-Core grants and bounded credential rotation, or fail closed. Do not enable topology B before these checks and cross-Core Agent/Repo Ops tests pass.

Two independent Bridges on one host must have distinct IPC endpoints, lease names, task state, process trees, recovery guards, private runtime directories, OS unit/task labels, logs and port allocations. Same-user ownership is an OS process-lifecycle boundary, NOT a hard isolation boundary between mutually untrusted users. The same canonical writable workdir must not be concurrently assigned to independent Bridges unless a proven cross-Bridge lock/lease mechanism coordinates all write/Repo/Agent operations. Initially reject such overlaps; overlapping read-only roots may be allowed when per-Core policy permits.

Ingress HTTP authentication and workdir access checks remain per request at Core. Sharing a Bridge or host user cannot expand a Core's authorized root set.

## 4. Migration, operation and release gates

1. Build and unit-test a pure cross-platform identifier/name contract, preserving all legacy default strings. This alone is **NOT** multi-instance support.
2. Add instance-aware *private* config/storage, registration, service state, readiness and independent lifecycles on Windows; preserve current W3 owner/guard rollback gate.
3. Add instance-aware SMAppService registration/bundle identity (not only CLI flags), credentials, data directories, and bridge endpoint/lease management on macOS.
4. Add per-Compose-project configuration/isolation and optional instance-scoped systemd user Bridge template/installer on Linux; preserve the shared-host Bridge mode.
5. Add a verified shared-Bridge client authorization protocol or explicitly mark B unsupported until complete. Add collision and overlapping-write-root negative tests.
6. Three-platform matrix: A/B/C/D, new instance creation, independent restart/stop/uninstall, transport + Agent/Repo Ops + revision/binary/cancellation, concurrent clients, policy denial, duplicate IDs, port/path/IPC clashes, upgrade/rollback and no change to unrelated production PIDs.
7. Public ChatGPT E2E plus out-of-band recovery and existing release requirements before declaring v0.25.0 ready.

All development until a separately approved operational gate is source-only. Do not touch live connectors/Bridges, credentials, retained provider guards or published tags.
