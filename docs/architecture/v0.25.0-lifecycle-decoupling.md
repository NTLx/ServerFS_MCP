# ADR v0.25.0 — Independent Ingress, MCP Core, and Agent Bridge Lifecycles

- **Status:** DRAFT / W0 **PASS for source-only W1** after no-loss Git fast-forward to `5e952cb9`; HTTP transport feasibility PASS in isolated W0. **W2/W3 live lifecycle, hosted ingress, credential migration and production cutover remain BLOCKED** until independently verified and separately authorized. Not a platform or release approval.
- **Date:** 2026-11-10
- **Scope:** ServerFS v0.25.0, design first on native Windows 11 x64; then macOS 27 arm64; Linux last.
- **Authority:** `dev_plan_v0.25.0.md` at the Windows ServerFS workdir root; current source, accepted tests, secure platform constraints, and sanitized `docs/diagnostics/v0250-windows-w0-baseline-2026-11-10.md`.
- **Release:** v0.24.2 is the current published stable release; v0.25.0 remains **IN DEVELOPMENT**.

## 1. Decision and open feasibility gate

**Decision on topology:** Three independent same-user lifecycles: OpenAI ingress and Cloudflare ingress are connector-only; one persistent MCP Core owns workdir policy and sessions; one independent Agent Bridge owns protected IPC, providers, deterministic Repo Ops and writer leases. No connector or Core may spawn/stop the Bridge. This three-layer requirement is firm.

**Updated preferred transport candidate, based on actual installed-client evidence (2026-11-10):** The WorkPC's `tunnel-client 0.0.17+a248b7f7` `run --help` advertises `--mcp.server-url` (Streamable HTTP target) and file-backed `--mcp.extra-headers` and `--mcp.discovery-extra-headers`. Current upstream project documentation also describes Streamable HTTP as a supported customer MCP transport (https://github.com/openai/tunnel-client/blob/master/docs/connectors.md and https://github.com/openai/tunnel-client/blob/master/docs/configuration.md). **Candidate B — OpenAI connector directly targeting the persistent HTTP Core — is now preferred** over a custom stdio bridge, *subject to isolated protocol/security acceptance*. The original plan's instruction **not to assume HTTP support** has been satisfied by evidence; it did not prohibit an evidenced alternative.

```text
ChatGPT/other MCP clients
         |                             |
    OpenAI Tunnel                 Cloudflare Tunnel
    (--mcp.server-url)               (HTTP origin)
         |                             |
         +--------- protected ---------+
                   HTTP /mcp
                       |
          persistent ServerFS MCP Core
          (policy + sessions + workdirs)
                       |
           authenticated local Bridge IPC
                       |
            independent Agent Bridge
         (single owner, provider tree, leases)
```

**Candidate A, fallback only:** A standards-compliant stdio↔HTTP adapter can be designed if the actual `server-url` protocol gate fails and the adapter independently passes *all* session/security/failure tests; do not build it speculatively. Legacy tunnel-owned supervisor/Core/Bridge remains a controlled migration/rollback path, not a v0.25.0 lifecycle design.

**W0 transport-feasibility result: PASS under a disposable real-binary loopback fixture, NOT yet hosted production parity.** The local Windows operator's 19:47–20:00 report confirms the installed `tunnel-client 0.0.17` `dev proxy --mcp-server-url` can carry genuine MCP initialize, tool calls, auth and Core-scoped HTTP sessions against an independently running ServerFS Core, and stopping the proxy leaves Core alive. It also reveals specific POST-versus-standalone-GET SSE limitations, Core credential injection and cross-ingress session handling. Overall **W0 remains BLOCKED** by no-loss source baseline reconciliation and final migration/security decisions; W2 must confirm the hosted OpenAI connector (non-production Tunnel identity) and full Agent/Repo, binary, progress and cancellation parity. No production credentials, jobs, ports or the existing `cmtools` guard were changed.

**Rejected:** transferring Bridge dependency to Cloudflare, putting Bridge inside Core, spawning Core per connection, weakening Host/API Key/authorization, indiscriminate service restart, unreviewed new resident helpers, privileged Windows services or self-terminating in-band handovers.

## 2. Component ownership contract

| Component | Owned process and OS lifecycle | Permitted dependencies | Must survive |
| --- | --- | --- | --- |
| OpenAI ingress | independently supervised tunnel-client directly using `--mcp.server-url` (or a separately accepted fallback stdio adapter) | authenticated persistent Core endpoint, control-plane credential | Cloudflare stop/restart; Core/Bridge may be temporarily unavailable without ingress owning their restart |
| Cloudflare ingress | independently supervised cloudflared only | public edge and authenticated loopback Core | OpenAI stop/restart; Core/Bridge independent |
| MCP Core | own persistent current-user task/service; Native TOML policy, MCP session manager, protected 127.0.0.1 HTTP listener | same-user authenticated Bridge IPC when Agent/Repo enabled | either ingress stop/restart; Bridge interruption leaves read/search/write file-only tools according to the existing policy |
| Agent Bridge | own persistent current-user task/service, unique private IPC identity | provider runtimes, one guarded SID/UID lease, Job/process tree containment | ingress and Core stop/restart; in-flight provider task state and writer lease survive a Core restart |

**Bridge failure behavior:** The Core keeps serving workdir-only tools; it must **not** silently enable Agent/Repo capabilities or restart Bridge. Any Agent/Repo call fails closed with an explicit non-secret unavailable/policy-mismatch diagnostic. If existing startup requires a Bridge policy-sync RPC and cannot start otherwise, change it narrowly, with tests proving both file-only survival and refusal of mismatched or unauthenticated Bridge use. A Core must not manufacture a prior-provider-termination proof.

**Policy convergence:** The Core is the single authoritative loader of native `serverfs.toml`. Both ingress transports must present the same effective aliases, read-only/default-write rules, deny globs, binary/Agent/Repo policy, and correct caller admission; no second writable configuration shadow, no ingress-specific privilege. Bridge validates policy fingerprints independently and fails closed on drift. Core authorization is checked for **every** request; authenticated ingress is not automatic filesystem authority beyond configured workdirs.

**Session ownership (measured):** The Core owns `Mcp-Session-Id` for the entire installation, not per Connector; an existing session was reused after restarting `dev proxy` on a different loopback port, and a new session was also created. Treat a session ID as a potentially replayable bearer-like handle, **never as proof of identity or authorization**. Authenticate each POST/GET at the Core and enforce per-tool policy. Do not silently claim ingress-specific session isolation. Explicit session invalidation after Core restart, TTL/expiry, and cross-credential/cross-origin authorization remain W2 verification.

## 3. Windows user-scoped lifecycle design (names tentative pending actual Task Scheduler registry inspection)

Retain Windows Task Scheduler 2.0, current user `InteractiveToken`, `LeastPrivilege`, logon trigger plus one-minute heartbeat, `IgnoreNew`, watchdog/runner with bounded restart policy, intentional-stop disable-before-terminate, validated manifests and frozen process identities.

Proposed logical services, after a collision-free task-name and state-root audit:

1. **Agent Bridge** (e.g. `ServerFS Agent Bridge`): own task/manifest/state/logs/runner/watchdog; the only holder of SID-scoped `LifecycleLease` and named kill-on-close `WindowsJob`. Bridge and provider descendants in the Bridge Job; no Core, tunnel or connector inside the Bridge Job. Preserve private bootstrap proof, authenticated named pipe, provider stop/recovery guards and lease semantics. Reject a second owner for the same SID even if a second ingress exists. Do not replace the named Job contract with a bare PID/lock.
2. **MCP Core** (e.g. `ServerFS MCP Core`): distinct task/manifest/state/logs, separate bounded runner, loopback-only origin and read/write/Agent/Repo policy loaded from canonical TOML. Its Job may contain its own Core worker but must not contain Bridge or ingress. The Core has no Cloudflare/OpenAI control-plane credential; an explicitly separate internal credential/OS identity boundary is required for any local listener.
3. **Cloudflare connector** (e.g. preserve/adapt `ServerFS Cloudflare WorkPC` only following migration review): reuses verified pinned cloudflared, token file and DACL/Authenticode checks and its own Task Scheduler owner. **Remove Origin process from connector generation** once independent Core is proven. Do not destroy the existing Origin+Connector production generation during W1/W2 or collide with its TCP 18765 origin port.
4. **OpenAI connector** (e.g. existing `ServerFS Native Tunnel` as optional product mode): tunnel-client configured for direct Streamable HTTP, with a thin stdio adapter only if separately justified and accepted; must not start/stop Core or Bridge. For the WorkPC's old tunnel, retire only after new Cloudflare path and independent Bridge are publicly verified, and only through authorized out-of-band W3 handover. Preserve optional OpenAI capability for other users.

Each service exposes component-scoped `install/start/status/stop/restart/uninstall`, with verified registered/enabled state, process identity, liveness, readiness, error and backward-compatibility diagnostics. Legacy generic `service stop`/restart/uninstall must not implicitly stop multiple layers; map to a single explicit component only where unambiguous, otherwise fail closed with migration guidance. No implicit privilege expansion, task replacement or credential rotation. No new generic always-on process or maintenance job beyond these three *actually required* service owners plus optional connector.

**Current OS registry evidence:** A non-elevated local FullLanguage operator directly confirmed `ServerFS Native Tunnel` and `ServerFS Cloudflare WorkPC` Running/enabled/valid (`Interactive`, `Limited`) with CLI agreement; earlier `registered=false` was a sandbox artifact. Other existing task names include `ServerFS Acceptance Runner Kill`, `ServerFS v0.17.1 Upgrade` and `ServerFS v0.22.0 Upgrade Temporary`; the last is enabled/Ready. Do not collide with or remove them without an explicit ownership/cleanup review. The process launcher uses shim→uv interpreter re-exec pairs; do not treat one logical component as always exactly one PID.

## 4. OpenAI HTTP upstream — mandatory transport and security gate

### 4.1 Verified discovery, distinguished from runtime acceptance

- Windows native operator report `docs/diagnostics/v0250-windows-w0-operator-report.md` records the *actual installed* `tunnel-client` binary `0.0.17+a248b7f7`, SHA-256 `61A770C759C386845F830A106F7E6D0D3F854B932259744A88B4013C282E64EC`, its `run --help` output and current live `--mcp.command` process ancestry.
- The binary advertises `--mcp.server-url` for HTTP targets, `--mcp.extra-headers` and `--mcp.discovery-extra-headers` with `env:`/`file:` value references, `--mcp.max-concurrent-requests` default 10 and `--mcp.connection-max-ttl` default 10 minutes.
- Published upstream documentation expressly supports a Streamable HTTP MCP target and explains channel binding, startup probing and separate HTTP discovery headers. **Do not infer the exact v0.0.17 implementation of every current upstream feature without an installed-binary probe.** Sources: https://github.com/openai/tunnel-client/blob/master/docs/configuration.md ; https://github.com/openai/tunnel-client/blob/master/docs/connectors.md .
- Existing product code `src/serverfs_mcp/native_tunnel.py` only creates `--mcp.command`; `tests/e2e/fake_tunnel_client.py` only implements that stdio mode. **No source/test support for HTTP-upstream product mode exists yet.** **Real isolated W0 protocol probe PASS** for initialize, tools, auth, file operations, revisions, dual-session correlation and Connector/Core process independence: `docs/diagnostics/v0250-windows-w0-http-upstream-report.md`. Hosted control-plane/OpenAI public E2E and several advanced semantics remain NOT VERIFIED.

### 4.2 Candidate B: direct HTTP to independent Core (preferred)

**Flow:** tunnel-client is independently supervised, configured to target the authenticated loopback-only persistent Core. It does not launch any Core/Bridge child. Cloudflare separately forwards to the *same* Core service, which owns one canonical workdir/policy, session manager and Bridge IPC client. This reduces a custom MCP protocol implementation and its ongoing maintenance cost.

**Auth and header risks must be proved, not assumed:**
- Keep the OpenAI control-plane API Key wholly separate from the Core resource-server credential. Store connector and HTTP authentication materials outside all exposed workdirs, using Windows owner/DACL and anti-reparse protections. Do not put secrets in literal argv, TOML or logs.
- **Measured static Core credential injection:** `dev proxy` has **no** `--mcp-extra-headers` flag. It nevertheless honored an explicit child-only `MCP_EXTRA_HEADERS="Authorization: Bearer <ephemeral test key>"` environment binding. Without it Core returned **401** and the connector attempted OAuth protected-resource metadata discovery, then failed readiness. The current `native_tunnel.py` scrub deliberately strips all `MCP_*` names; W1 must pass **only** an explicit validated narrow `MCP_EXTRA_HEADERS` configuration to the connector child, never copy the ambient `MCP_*` environment. Production preference: `file:`-backed full Authorization header value held in a private file outside workdirs with protected DACL; **this file-resolution path was not exercised in W0**, so test it before relying on it. Do not put literal secrets into argv, manifests, logs or repo TOML.
- **Measured conflicting forwarded Authorization:** client-provided bad `Authorization` overrides the static header and Core returns **401 fail closed**; supplying a correct key returns 200. Upstream documentation confirms connector-forwarded headers override static headers. Do not turn static headers into an authorization bypass, and distinguish startup/discovery `MCP_DISCOVERY_EXTRA_HEADERS` from runtime headers; their precedence under a real hosted Tunnel is **NOT VERIFIED**.
- Validate the Core's allowed Host/Origin for **each** ingress' actual HTTP Host; retain exact allowlists and no wildcard. Prevent proxy inheritance for loopback target, SSRF or cross-origin redirect credential forwarding. Distinguish HTTP loopback authentication from Bridge IPC SID identity.
- **Measured HTTP security/session responses:** invalid Host yielded **421** (verified by raw socket; an `httpx2` malformed-host probe spuriously yielded 502), wrong Origin **403**, absent Origin allowed (non-browser), absent backend authorization **401**, stale session **404**. Core session survived 65s idle and reused across a new proxy process. Preserve exact Host allowlist and bounded session lifetime; no caller bypass from loopback or forwarded headers.
- **Measured SSE limitation:** same-session standalone HTTP `GET` via **local `dev proxy` ingress** returned **501**, whereas directly connecting to Core returned SSE 200 and remained open **75.1s**. The negotiated `MCP 2025-06-18` supports optional standalone GET SSE; its absence does **not** by itself prove POST-based request SSE or ServerFS task event functionality broken. But the proxy's 501 is not proof of acceptable GET behavior for clients relying on server-initiated messages, and a stdio adapter is **not automatically a fix** for an ingress-level GET 501. W2 MUST verify actual hosted transport, POST streaming of long requests, notifications/progress/cancellation/Agent event semantics, and document either full parity or an explicit reviewed feature boundary. Do not silently lower capability.
- The `--mcp.connection-max-ttl=10m` default is a **connection TTL**, not an established 10-minute MCP Session or SSE lifetime. Test actual >60s POST response streaming, reconnect and behavior across a measured TTL; W0 dev proxy did not expose a shorter TTL, so its effect remains **NOT VERIFIED**. Never claim guaranteed replay/persistence from this flag.

**What this passes:** native direct HTTP upstream to an independently hosted authenticated Core, with real MCP control/message/schema semantics and basic security. It invalidates the necessity of implementing a custom stdio adapter merely to reach Core.

**What it does not pass:** full hosted Tunnel/OpenAI public transport; server-initiated standalone GET; long POST SSE/progress/cancellation; binary/Agent/Repo; independent Bridge/OS service ownership; policy fingerprint; release acceptance. A local `dev proxy` 501 cannot be assumed to occur identically at a hosted Tunnel, and it cannot be silently dismissed. Both directions remain to be measured in W2 with a dedicated, non-production Tunnel identity.

### 4.3.1 W1/W2 negative gates triggered by W0 evidence

1. Use explicit, least-privilege per-Connector `MCP_EXTRA_HEADERS` injection for the **HTTP backend only**; keep `native_tunnel.py` ambient-env scrubbing for all other `MCP_*` and provider variables. Prefer OS-protected `file:` reference with verified installed-client semantics; W0 tested a scoped literal only in ephemeral child env. On missing/wrong credential startup must fail closed with sanitized 401/metadata-discovery diagnostics.
2. Verify both `MCP_EXTRA_HEADERS` and `MCP_DISCOVERY_EXTRA_HEADERS` during startup probe and actual MCP calls; test user-forwarded `Authorization` conflict and exact Host/Origin on the full hosted path. Do not bypass backend authentication or use repo-root `.env`.
3. Prove **long-lived POST-based MCP SSE**, progress/cancellation/event access and 10m client TTL as relevant. For 2025-06-18 standalone GET is a protocol-optional stream, but when a publicly supported ServerFS feature **requires** it, no release gate can be waived. If parity fails, either prove a separately reviewed alternative transport or mark gate FAIL/BLOCKED. A stdio adapter does not automatically solve ingress-GET behavior.
4. Treat `Mcp-Session-Id` as Core-global and untrusted as authentication; verify per-request credentials, denial of cross-origin/tenant privilege escalation and session invalidation after Core reset.
5. After implementation, test stopping connector leaves **Core and Bridge** alive, stopping Core leaves **Bridge and providers** alive, and refusal of a second Bridge owner. A process list alone cannot prove job/lease containment.
6. Retain the original file/Agent/Repo/binary/rollback/public E2E acceptance matrix without reducing scope.

### 4.4 Candidate A fallback

If required, a disposable stdio MCP server process may use the existing MCP SDK's Streamable HTTP client to a persistent Core. It must faithfully map initialize, notifications, request IDs, errors, progress, cancellation, binary results and stateful HTTP session lifecycle; preserve authentication and per-connection isolation; and never own Core or Bridge. This approach has higher implementation and regression cost and is **not** the default after the observed installed-client HTTP support.

## 5. Host and credential boundary

- Core HTTP listens exclusively on `127.0.0.1` with an exact allowed Host/Origin and an authenticated resource-server boundary; don't treat localhost as an implicit no-auth bypass. Use the existing API Key/OAuth middleware where possible, with a separately scoped internal credential for a stdio adapter only if independently protected and justified.
- File and Bridge authorization must continue to enforce explicit read/write/revision, hidden/deny, link/reparse and traversal protections, private credential exclusion, binary opt-in and active writer leases. Never forward provider environment wholesale to Core/connector or weaken the Windows kernel containment/ACL model.
- Private Windows Connector Token and Origin/adapter credential files remain outside all MCP-exposed roots and are validated for current-user owner SID, protected DACL, fixed executable identity, and no inherited/writable foreign ACEs. Log only presence, hashes, paths classified as private and booleans; never token/key values.
- Use only available explicit ServerFS MCP tools and deterministic Repo Ops. No general-purpose local command endpoint, agent fallback for Repo Ops or automatic task approval.

## 6. Safe staging, W3 cutover and rollback state machine

**Before staging:** freeze reviewed evidence of original task XML/manifests, installed environments/wheel hashes, canonical TOML policy fingerprints, credential path/ACL metadata, the old job/lease identity, active task and provider descendant list, writer lease/recovery guards and the public ChatGPT baseline. Store rollback artifacts **outside MCP-exposed roots**. Do not capture secret contents in reports.

**Staging:** implement source/test against an isolated non-admin identity and separate Core/connector ports; separate watched tasks must be disabled by default and may not collide with existing SID pipe/lease or production port. A same-SID parallel Bridge fixture cannot run against production's unique owner. The test must use an isolated host/user or an explicitly designed and verified test-only namespace with no production endpoints/roots; otherwise Windows W2 must be recorded BLOCKED, not bypassed.

**Migration states:**

```text
LEGACY_LIVE
  -> PRECHECKED (real task/lease/guard/provider ownership verified; no unsafe in-flight writes)
  -> STAGED (new artifacts validated; rollback complete; new Bridge owner NOT yet active)
  -> QUIESCED (new tasks held; safe handover authority out-of-band)
  -> LEGACY_OWNER_STOPPED (verified old Bridge/provider Job stop and lease release)
  -> NEW_BRIDGE_READY (unique owner, secure IPC and recovery verified)
  -> NEW_CORE_READY (independent Core; identical effective policy)
  -> NEW_CLOUDFLARE_PUBLIC_E2E (verified ChatGPT + Agent + Repo + file security)
  -> RETIRE_OLD_CONNECTOR (only with explicit operator approval)
  -> ACCEPTED
```

The transition that stops the legacy Bridge **cannot** be assigned to an Agent running inside that Bridge; it would kill the only control channel. Use a narrowly scoped operator-controlled same-user scheduled **one-shot** or explicitly human-run host step with a persistent journal, bounded timeouts and a proven external rollback trigger. Do not introduce an uncontrolled persistent helper. If Scheduler permission checks fail in an Agent sandbox, stop and request **minimal non-elevated host action**, not a bypass.

**Rollback:** Before old owner stop, restore/retain original services unchanged. After a failed handover, stop only the new independent owner through the out-of-band control path; verify the new Bridge Job termination and exclusive lease release before reactivating the known-good legacy owner; restore old Cloudflare origin target; verify actual public ChatGPT MCP and task state. Never run old and new Bridge owners concurrently, delete unknown guard files, terminate by process name alone, or remove old plugin before E2E. A Bridge failure must not trigger automatic Core/connector process termination.

## 11. W1b implementation refinement — source only, not accepted

The first Windows separation is an independent **Bridge-only** service boundary, not a new Tunnel parent. The Bridge task manifest and native state are independent from the two currently running ingress owners; no existing task registration, running process or live credential has been modified.

The Runner is created suspended, assigned to its own Job before resume, and its child environment drops control-plane/tunnel/OpenAI/MCP/ambient proxy/PYTHONPATH-style values. Actual wheel/ABI and Windows nested Job behavior remain native W2 gates.

**Generation-health proof:** a `bridge.ping` on the existing SID-derived pipe can still be answered by the *legacy production Bridge* even if the newly launched owner failed. Thus W1b-2 currently watches **its own Runner process identity/exit** and deliberately does not claim the SID pipe's response as a new generation. A hung living Bridge is not automatically detected; generation-bound authenticated readiness/IPC ownership and bounded unresponsive recovery must be added before W1b acceptance. Existing `cmtools` recovery guard and provider ownership must never be inferred from task count or unbound IPC response.

**Remaining W1b gates:** transactional disabled-by-default Task Scheduler installation, protected private service-home/ACL, exact same-user SID and code-image verification, task-scoped start/stop/restart/uninstall and intentional-stop invariants, graceful out-of-band stop/rollback, and actual Windows pytest/Ruff/native Job+IPC acceptance. ## 12. W1c/W1d independent Core and connector-only source refinement — 2026-11-11

**Core is not the Bridge owner.** The proposed `ServerFS MCP Core` Task Scheduler unit directly starts `pythonw.exe -I -m serverfs_mcp.windows_core_service _run` in its own installed user-level interpreter and invokes existing native `serve --transport streamable-http` logic. It only holds HTTP MCP sessions/workdir policy and accesses the already-owned Bridge as an authenticated client. No second HTTP SDK, raw HTTP proxy, stdio supervisor, Bridge launcher or provider process is introduced. The Core task is disabled by default and must be explicitly accepted with private DACL and real PID/socket identity evidence before enabling.

**Exact dual ingress Host:** the Core is bound to `127.0.0.1`; the trusted `SERVERFS_HTTP_ALLOWED_HOSTS` is exactly a two-element set: Cloudflare's intended public Host and `127.0.0.1:<core-port>` for OpenAI's HTTP upstream. Wildcards, arbitrary Host aliases, and uncontrolled Origin are not valid defaults. Existing API Key/OAuth verification and native workdir policy remain in force. A private credential env file is validated by the existing Win32 SID/DACL/no-reparse validator and must be outside every exposed workdir.

**Connectors are peers, not parents.** The Cloudflare connector-only process is contained within its own Job; stopping it must not close Core or Bridge. A 401 probe is necessary but can target the old live Cloudflare Origin, so an independent signed task/PID/creation-time/listener-ownership proof must be implemented before this generation can be launched safely. The OpenAI connector instead supplies `--mcp.server-url` to the already-running HTTP Core and passes its control-plane key and Core Origin `Authorization` header via private `file:` value references, not env/argv plaintext; it never uses `--mcp.command` in connector-only mode. The old stdio Supervisor is retained for historical rollback until final migration.

**Identity and verification:** a Core process PID alone, a 401 response alone, the mere presence of a named Bridge pipe, and a successful Task Scheduler `/Run` are independently insufficient proofs. W2 must observe Core task ownership, matching Core listener, Agent Bridge generation and policy equality, and connector PID/job ownership; hosted OpenAI full duplex/SSE semantics and authenticated cross-ingress tools remain acceptance gates. The Windows W1c/W1d source implementation is **NOT** a native acceptance claim. Reference: `docs/diagnostics/v0250-windows-w1c-w1d-core-ingress-source-review-2026-11-11.md`.

## 13. Core W1e single-owner and safe Task Scheduler staging — source only

The independent Windows Core is now restricted to a fixed, current-user `ServerFS MCP Core` Task Scheduler contract. Installing it **never** overwrites a task and requires an operator-prepared, owner-verified, protected-DACL private directory in the Win32 current-user Known Folder; `core-owner-env`, manifest, task XML and state are similarly checked. Initial registration is disabled. Any nonzero `/Create` return with an unexpectedly existing registration is an **ambiguous result**: preserve task and evidence, do not remove an unknown task. A valid rollback requires the exact registered task to remain disabled, never started and contract-matched.

Before the existing Streamable HTTP MCP SDK binds to `127.0.0.1`, Core must hold a SID-scoped **Core-only named mutex** and match its own current-process executable, PID creation-time, registered XML, authored task hash, config path, API auth file, port, public Host and current user. A prior recorded Core process with the same image and creation time must have exited; an unreadable but present PID is not treated as a terminated owner. This mutex is not a Bridge or Connector parent. Active stop/restart and cutover are not implemented; stop/uninstall only apply to a disabled, never-started staged Core. A read-only status deliberately distinguishes task registration, recorded process identity, **unknown port-listener ownership**, and **unverified HTTP readiness**.

Native acceptance must still prove the registered task owns the live listening TCP socket, as observed via Windows OS APIs, and that its hosted HTTP identity is bound to the correct authenticated process generation (not a legacy Origin returning 401). W1e did not attempt task registration or execute Windows pytest/Ruff. Evidence: `docs/diagnostics/v0250-windows-w1e-core-control-source-review-2026-11-11.md`.

## 14. W1f Core TCP listener and independent connector ownership — source only

**Socket identity is not HTTP response identity.** The new Windows native `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_LISTENER)` proof joins an exact loopback 127.0.0.1 TCP listening row to the registered `ServerFS MCP Core` Task Scheduler contract, private manifest, SID, and same-process PID+creation-time+image evidence. Only one exact owner row is allowed; foreign, wildcard, missing or duplicate rows fail closed. Core-only status can report socket owner verified but still reports HTTP protocol/credential readiness as **not verified**. A second kernel process check reduces PID-reuse races.

**OpenAI and Cloudflare Connector are independently scheduled peers.** `ServerFS OpenAI Connector` and `ServerFS Cloudflare Connector` each own a different `pythonw -I` launcher, private policy/manifest/state files, SID-scoped mutex, and exactly one anonymous kill-on-close Job containing only its connector binary. Each verifies Core ownership before launch and periodically thereafter, then closes **its own** job on failure. Neither connector starts/restarts/kills Core, Bridge, a different connector, or the historical legacy owners.

**Private file contract:** mutable source artifacts must be created only inside a pre-provisioned private user-owned service home and explicitly receive a protected DACL before publication. The Windows `SetNamedSecurityInfoW` helper is restricted to newly created private temporary artifacts; credential files, source/workdirs and installed legacy services are not rewritten. Task installation is disabled and can roll back only a proven never-started exact component; ambiguous Scheduler state is retained for diagnosis.

W1f source/tests are **not Windows-native acceptance**. Win32 ctypes signatures, DACL installation and race behavior, TCP owner table, Job nesting, Scheduler transitions, HTTP protocol, public Tunnel routing and out-of-band rollback require real Windows isolated tests before W2/W3. Reference: `docs/diagnostics/v0250-windows-w1f-core-listener-connectors-review-2026-11-11.md`.
