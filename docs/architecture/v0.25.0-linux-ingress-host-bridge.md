# ADR v0.25.0 — Linux Ingress Combinations and Host-native Agent Bridge

- **Status:** ACCEPTED Linux design constraints (2026-11-18).
- **Scope:** Linux deployment only. Source/deployment implementation and runtime acceptance are separate gates; this ADR does not claim that all combinations are implemented.
- **Platform policy:** Docker-first for MCP Core and optional ingress connectors; host-native Agent Bridge by default. **Not** Docker-only.
- **Related contracts:** `v0.25.0-instance-model.md`, `v0.25.0-lifecycle-decoupling.md`, `v0.25.0-native-platform-boundaries.md`.
- **Production safety:** Source-only design change. No migration, live service modification, credential rotation, Git integration, or publication is authorized by this document.

## 1. LNX-001 — Three ingress choices, independently composable

Every Linux MCP Core is a persistent HTTP MCP service. The following ingress choices MUST be supported without changing the Core's tool behavior, filesystem policy, or session ownership:

1. **Cloudflare Tunnel:** optional, independently managed `cloudflared` Docker service; it forwards authenticated MCP HTTP traffic to the Core.
2. **OpenAI Tunnel:** optional, independently managed `tunnel-client` Docker service; it connects to the same HTTP Core (using a verified supported HTTP upstream mode).
3. **Direct HTTP:** optional Docker host-port publication of the Core's HTTP MCP listener, with no Tunnel required. This is a Core deployment option, **not** a third connector process.

Cloudflare and OpenAI connectors MAY be enabled independently or together. Host-port publication MAY independently be enabled or disabled. With neither Tunnel nor published port, the Core MAY remain reachable only on its explicitly authorized internal Docker network. No Cloudflare/OpenAI control-plane credentials may be required for a direct-HTTP-only instance.

| Cloudflare | OpenAI | Published HTTP port | Required result |
| --- | --- | --- | --- |
| off | off | on | Direct HTTP MCP |
| on | off | optional | Cloudflare MCP, optionally also direct HTTP |
| off | on | optional | OpenAI MCP, optionally also direct HTTP |
| on | on | optional | Both tunnels target the same independent Core, optionally also direct HTTP |
| off | off | off | Internal-only Core; no public ingress |

**Lifecycle contract:** Each connector owns only its own process, credentials and transport. Restarting, stopping or replacing one connector MUST NOT stop, restart or recreate the Core, another connector or the Bridge. Core and Bridge ownership remain independent. Transient unavailability must not silently expand permissions or cause connectors to spawn their dependencies.

**Direct HTTP security:** The default host-port binding MUST be loopback-only (`127.0.0.1`), with wider host interfaces available only by explicit opt-in. A published port is not equivalent to authorized access: Core authentication and per-request workdir/tool policy continue to apply. Reverse proxies, TLS termination, certificate issuance, public DNS and external ingress configuration are **out of project scope**; ServerFS must not automatically manage them.

**Compatibility:** Existing deployments, service identities, authentication contracts and tunnel resources are not implicitly migrated or renamed. The new Linux layout must not convert the legacy OpenAI default into a required service for direct-HTTP or Cloudflare-only deployments.

## 2. LNX-002 — Host-native Agent Bridge is the Linux default

The MCP Core and optional ingress connectors MUST run as Docker services. The Linux Agent Bridge MUST remain usable as a **separately managed host-user process**, reusing the host's installed Codex, Claude Code, Qoder and other explicitly supported Agent runtimes and their existing user-scoped configurations.

The default integration is:

```text
Cloudflare container ----\
OpenAI container ---------+--> persistent MCP Core container(s)
Direct host HTTP port ---/             |
                                  authenticated
                                    Unix IPC
                                        |
                          host-native Agent Bridge
                           (user-level lifecycle)
                                        |
                         host-installed Agent runtimes
```

- Reuse the existing Linux host-Bridge architecture, including the user-scoped systemd service and the Core-side Unix socket bind mount, where supported and proven. Do not replace it merely for container uniformity.
- A Core with `bridge_mode=disabled` MUST run without Bridge installation, Bridge socket, host Agent runtime or Agent credential prerequisites.
- `bridge_mode=owned` identifies a Bridge whose lifecycle is explicitly owned by that installation; `bridge_mode=shared` references a separately owned existing Bridge. These modes describe ownership, **not** whether the Bridge is containerized.
- In shared mode, multiple independent Cores MAY reference a single host Bridge only after per-Core identity, explicit grants, policy revision, workdir/operation limits, revocation, replay resistance and cross-Core task/result isolation pass real acceptance tests. A shared Core MUST NOT start, stop, uninstall, upgrade or reconfigure the owner Bridge.
- Independently owned Bridges require distinct private sockets, service identities, credentials, persistent state and task/lease ownership. Reject unsafe writable-root overlaps; do not infer trust from a shared UID or socket alone.
- The Core-to-Bridge IPC and host/container workdir path translation MUST be explicit and validated. A Core's bind-mounted workdir authorization cannot grant wider host filesystem access through the Bridge.
- The host Bridge uses least-privileged user-level execution and protected socket/credential paths. Do not mount host Agent credentials into the Core, expose the Docker daemon socket, request `privileged` containers, or introduce a central privileged supervisor to achieve host Agent execution.

**Non-goal for v0.25.0:** Repackaging the Bridge or all existing Agent CLI installations inside Docker is not required. A future optional containerized Bridge may be considered separately only if it adds demonstrated value and maintains the same security and lifecycle behavior. Reusing host-installed executables does **not** imply attaching to pre-existing interactive Agent sessions; such session reuse requires separate provider-specific evidence.

## 3. Linux implementation boundaries and coexistence

- One or more independent Docker Compose projects can host separate MCP Core instances with unique `instance_id`, config, ports, state and isolated networks. Connectors carry independent `connector_id`; host Bridges use independent `bridge_id`.
- Use Linux-native host service supervision for a host Bridge, not a second application-level instance manager. Docker Compose remains the orchestrator for containerized components; systemd user units remain the optional/owned host process mechanism.
- Preserve the existing `default` deployment and its resources unless a separate explicit migration is accepted. New instances must not reuse another instance's writable state, credentials, listening socket or TCP bind.
- Prefer Linux-specific files under `deployment/linux/` and Linux-scoped tests/docs; changes to common Core/Bridge modules, dependency lockfiles, common CI or release metadata require cross-platform reconciliation with ongoing Windows/macOS work.

## 4. Required source and live acceptance gates

1. **Ingress matrix:** prove direct HTTP without Tunnel credentials; Cloudflare-only; OpenAI-only; both tunnels; and combinations with/without host-port publication. Verify MCP initialize, tool discovery/calls, authentication and denial paths through each enabled ingress.
2. **Lifecycle independence:** stop/restart each connector while Core and Bridge remain alive; stop/restart Core without implicitly stopping an owned/shared Bridge; verify file-only behavior during Bridge outage.
3. **Host Agent reuse:** confirm host Bridge launches the actually installed supported Agent CLIs using host-side credentials/configuration without copying runtimes into images; verify real Agent operation and Repo Ops end to end.
4. **Bridge modes and security:** disabled mode has no host Bridge requirement; owned/shared work correctly; negative tests cover unregistered/revoked Core, stale policy, replay, cross-Core task visibility, unauthorized workdirs, write-root overlap, invalid socket access and mismatched host/container path mappings.
5. **Multi-instance / rollback:** separate Compose projects and Bridge instances do not collide on ports, volumes, credentials, sockets or leases; independently stop/uninstall a new test instance without changing existing production process identities.
6. **Release integration:** test the public MCP behavioral/security contract and exact release candidate on Linux independently of Windows and macOS; do not report production acceptance on source tests alone.

**Gate rule:** All changes to deployed services, external DNS/Tunnel resources, live credentials, production Compose projects or systemd units require a separate operational approval. This ADR alone authorizes none of them.
