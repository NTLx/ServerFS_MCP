## 2. Real current-user AF_UNIX RPC and CLI acceptance

A temporary config enabled only the existing deterministic `fake` runtime, set the
Bridge socket/state/lock paths beneath a fresh temporary directory, allowed the current
UID/GID, and pointed its sole writable policy at another temporary directory. The
Bridge ran as UID 1000 (`lx`); no root operation was used. Its socket was owned by UID
1000 with mode `0660`. The existing `task.submit` private RPC created a task through the
normal protocol and the task reached `succeeded` before diagnostics were queried.
The Bridge process command was:

```bash
agent_bridge/.venv/bin/serverfs-agent-bridge --config "$TMP/bridge-config.json"
```

The config used the temporary socket, state and lock paths; `allowed_peer_uid` and
`allowed_peer_gid` were the values from `id -u` and `id -g`; fake runtime was enabled;
and the only writable workdir policy pointed to `$TMP/workdir`. The submit request used
these parameters over a newline-delimited protocol-v1 frame:

```json
{"runtime":"fake","workdir":"scratch","path":"","profile":"review","prompt":"complete:phase-f-local-acceptance"}
```

Subsequent `task.get` requests polled the returned task ID until its terminal state.

The root CLI was invoked directly with the temporary socket in
`SERVERFS_AGENT_BRIDGE_SOCKET`:

```bash
SERVERFS_AGENT_BRIDGE_SOCKET="$SOCKET" uv run serverfs diagnostics snapshot --format json
SERVERFS_AGENT_BRIDGE_SOCKET="$SOCKET" uv run serverfs diagnostics snapshot
SERVERFS_AGENT_BRIDGE_SOCKET="$SOCKET" uv run serverfs diagnostics task "$TASK_ID" --format json
SERVERFS_AGENT_BRIDGE_SOCKET="$SOCKET" uv run serverfs diagnostics task "$TASK_ID"
```

All four commands returned **exit 0**. JSON and human output both reported one retained
terminal task; task output agreed on `available`, `succeeded`, `complete`, four bounded
operations and the same terminal seal/rollups. The real task ID was
`agt_b6dbba986870703b469f9db0` for this run. Each CLI invocation wrote its report only
to stdout and wrote **0 bytes to stderr**.

The Bridge was started as a child process with stdout/stderr captured. It wrote **0 bytes
to stdout** and exited cleanly after termination. RPC requests used the existing
AF_UNIX `BridgeProtocolServer`; the Bridge's existing SO_PEERCRED UID/GID authorization
was active. No listener, endpoint, or peer check was added or bypassed.

## 4. Linux endpoint fix discovered by live acceptance

The first actual root CLI invocation on Linux failed before connecting: diagnostics
called the native endpoint resolver, which attempted Windows SID/Named Pipe derivation
and raised because Linux has no `ctypes.WinDLL`. The Linux diagnostics command now uses
the existing `SERVERFS_AGENT_BRIDGE_SOCKET` setting, falling back to the established
Linux Bridge default `/run/serverfs-agent-bridge/bridge.sock`. This is limited to
diagnostics and does not change native serve lifecycle or IPC authorization. The
targeted tests and full root suite passed after the fix.
