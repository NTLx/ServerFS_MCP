# ServerFS v0.21.0 Phase G — Compatibility, Rollback & Non-goal Review

Date: 2026-10-22.

## Verdict

**Criterion 11: PASS.** The reviewed v0.21 delta preserves the existing product and lifecycle boundaries, adds only opt-in operator status formats and internal process-local observations, requires no persistent-state migration, and retains a source rollback point. The explicit prohibited-feature scan found no v0.21 implementation of any listed non-goal.

This is a source/history review, not a release or deployment action. v0.20.0 is the accepted but **unreleased implementation baseline** at commit `1de9428` (`docs: accept v0.20 implementation`). v0.19.0, tag `v0.19.0` (`650d6fe`), remains the **stable release**. There is no `v0.20.0` tag in this checkout. Do not describe the accepted v0.20 implementation as a shipped release.

## Reviewed evidence and scope

- Compared the complete v0.21 history after `1de9428` through `87494c4` using `git log`, `git diff 1de9428..HEAD`, and the changed-path list. This delta contains the observation contract, common native service-status projection, Bridge-local observations, associated tests, phase evidence, current-state documentation and version metadata.
- Read `dev_plan_v0.21.md` §14 and the Phase A–F evidence, particularly the Phase C status compatibility contract, Phase D persistence/performance notes, Phase E exporter decision, and Phase F platform acceptance and limitations.
- Inspected the actual CLI diff and the changed implementation/test paths against the v0.20 tree. The state-store schema implementation (`agent_bridge/src/serverfs_agent_bridge/store.py`), MCP tool/transport/auth implementations, and platform lifecycle implementations are unchanged in the v0.21 implementation diff.
- This review does not rerun suites. Validation for this task is limited to `git diff --check` and changed-path verification, as requested.

## Rollback procedure and effect

1. **If reverting an unreleased v0.21 implementation in a source deployment:** restore/redeploy the retained v0.20 implementation baseline (`1de9428`) using the matching v0.20 source/configuration. No migration reversal is required. Keep the operator's configuration and existing Windows/macOS service registrations; the new code has not changed their formats or owners.
2. **If rollback must land on a released artifact:** v0.20 is not a released rollback artifact. Select the retained v0.19.0 release artifact/tag and use that release's deployment procedure. Preserve configuration and service registration; status observations have no durable state to remove.
3. **After a v0.21 stable tag exists:** never move or recreate that tag. Corrections belong on the development branch and a separately authorized patch release. Release publication and Git operations are outside this review authorization.

## Criterion 11 decision

**PASS.** Compatibility is preserved by default, new common output is opt-in, persistence/configuration/lifecycle boundaries are unchanged, rollback has a no-migration path with the unreleased-v0.20 versus stable-v0.19 distinction explicit, and the prohibited-feature scan is clear. This verdict does not upgrade the Phase F `Not verified` items or claim a deployed v0.21 runtime was tested.
