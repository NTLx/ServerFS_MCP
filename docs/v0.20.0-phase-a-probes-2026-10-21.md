The actual `MCPServer` constructor has no `stateless_http` or server-discovery argument. Statelessness is selected when constructing the HTTP ASGI app. The server's configured product entry point calls `run("streamable-http", ...)` without passing `stateless_http`; the SDK default is therefore stateful HTTP. The API Key runner also builds the app without `stateless_http`, so it is stateful. The OAuth and API Key E2E fixtures explicitly build `stateless_http=False` apps. The security test separately exercises an app with `stateless_http=True`, but does not establish modern lifecycle compatibility.

`tests/test_mcp_protocol_compat.py` exercises the SDK's in-memory `Client(server)` lifecycle with `mode="2026-07-28"` and `mode="legacy"`; the latter negotiates `2025-11-25`. It checks tool listing and one tool call under each. OAuth E2E additionally proves that the HTTP initialize handshake responds with `2025-11-25`, and uses a modern `2026-07-28` HTTP client for a separate roundtrip. Existing accepted evidence in [`docs/v0.15.0-linux-chatgpt-live-acceptance-2026-10-19.md`](v0.15.0-linux-chatgpt-live-acceptance-2026-10-19.md) records transient real HTTP use by both client modes.

## 2. Official MCP Conformance CLI

Official source: [modelcontextprotocol/conformance README](https://github.com/modelcontextprotocol/conformance/blob/main/README.md), [npm package](https://www.npmjs.com/package/@modelcontextprotocol/conformance).

Read-only local probe of the explicitly pinned `@modelcontextprotocol/conformance@0.1.16` returned version `0.1.16`. Its `list --help` accepts `--client`, `--server`, and `--spec-version`; its `server --help` accepts URL, scenario/suite, expected-failures, output directory and spec-version. **It does not accept `--requirements`.** The attempted `list --requirements 2025-11-25` exited with `error: unknown option '--requirements'`; the chained command therefore did not reach the second requirement set. No ServerFS service was started.

The Phase A local probe above remains a historical observation: the explicitly pinned `0.1.16` CLI rejected `--requirements`, and no ServerFS service or conformance run was started. Subsequent verification against the official repository establishes that `--requirements` was introduced by commit [`232a9014457eaf4c59559916e3d616d2f7f28f05`](https://github.com/modelcontextprotocol/conformance/commit/232a9014457eaf4c59559916e3d616d2f7f28f05), merged as [PR #447](https://github.com/modelcontextprotocol/conformance/pull/447) on 2026-08-07. The official [releases page](https://github.com/modelcontextprotocol/conformance/releases) still marks `v0.1.16` (released 2026-03-27) as Latest as of 2026-10-21. Therefore, no stable release combines the frozen requirements feature with a released package. The official moving `main` README documents the commands:

```bash
npx @modelcontextprotocol/conformance list --requirements 2025-11-25
npx @modelcontextprotocol/conformance list --requirements 2026-07-28
npx @modelcontextprotocol/conformance server --url http://localhost:3000/mcp --requirements 2026-07-28
```

The README states that dated pre-modern revisions use initialize/session lifecycle, while `2026-07-28` uses stateless requests with per-request `_meta`; each requirement set must run at its own wire revision. The `0.1.16` local probe remains evidence for that release only. As of 2026-10-21, there is no stable release with frozen requirements support. For Phase C, either build and run conformance from the immutable commit `232a9014457eaf4c59559916e3d616d2f7f28f05`, or wait for a formal release that contains it. Do not use floating `main`, `latest`, or `alpha` as the reproducible gate.

The command was deliberately not retried after the unsupported option was observed. No client CLI run, server CLI run, `tier-check`, or requirement-list output was obtained. Those are **Not verified**.

## Phase B — real loopback compatibility probe (2026-10-21)

This later probe supersedes the Phase A preliminary conclusions stated in §1 and the old Phase B decision items above where explicitly indicated. Phase A's discovery-time limits remain historical context; the evidence below is the current observed result. Probe scope was a real loopback HTTP wire exchange using `mcp==2.3.0` and the stateful Streamable HTTP app.

### Observed results

- The same stateful app served both legacy protocol `2025-11-25` and modern protocol `2026-07-28`.
- The modern client succeeded against the stateful app without a session. Stateful app construction therefore does not by itself require a session for modern requests.
- For modern requests, the wire observation included `_meta` in the JSON-RPC request and these HTTP headers:

  ```text
  Mcp-Protocol-Version: 2026-07-28
  Mcp-Method: tools/call
  Mcp-Name: <the called tool name>
  ```

  `Mcp-Method` and `Mcp-Name` were observed on the modern tool-call request; the probe record preserves the called-tool relationship but not its literal name. These are method/name context headers, not replacements for JSON-RPC `method`/`params`.
- With client `mode="auto"`, the SDK issued `server/discover` and then continued using modern `2026-07-28`. SDK auto-discovery handled the discover exchange; no application-supplied `MCPServer` constructor option was needed.

### Four-cell compatibility matrix

| HTTP app / client protocol | Legacy `2025-11-25` | Modern `2026-07-28` |
|---|---|---|
| Stateful (`stateless_http=False`) | **Observed:** served with full session lifecycle | **Observed:** served without a session; modern `_meta` and protocol headers observed |
| Stateless (`stateless_http=True`) | **Observed:** served, but no session ID was allocated and no session `DELETE` occurred | **Observed:** served without a session; modern `_meta` and protocol headers observed |

All four app/protocol combinations were exercised in the real loopback probe. Stateless legacy succeeds at the request level, but does not provide legacy session semantics (session ID allocation and session `DELETE`).

### Updated implementation decision

Production HTTP remains **stateful** because ServerFS must preserve the complete legacy session semantics, including session ID allocation and session `DELETE`; the stateless legacy probe succeeded but omitted both. Phase B prioritizes real loopback wire regression tests for the observed legacy and modern behavior, including modern `_meta`, `Mcp-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, and the SDK `mode="auto"` discover path. **Do not change transport authority or the endpoint** as part of this compatibility work.
